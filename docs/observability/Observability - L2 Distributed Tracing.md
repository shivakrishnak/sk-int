# Distributed Tracing with Jaeger

**TL;DR** - Jaeger is a distributed trace collection and visualization
platform. It receives OpenTelemetry spans via OTLP, stores them in
Cassandra or Elasticsearch, and provides a UI for trace search and
Gantt chart visualization. Understanding Jaeger's architecture is
essential for operating distributed tracing in production.

---

**3 minutes (Senior):**

> backend for Kubernetes environments. The architecture has four
> components: the Jaeger Agent (now replaced by OTel Collector in
> modern deployments), the Jaeger Collector that receives spans via
> OTLP or Jaeger's native protocol and writes to storage, the
> storage backend (Elasticsearch for production, Cassandra as an
> alternative, Badger for all-in-one development), and the Jaeger

> the Jaeger Operator manages the Jaeger instance via a Jaeger CRD.

> in 2025 is Grafana Tempo: a Prometheus-native distributed trace
> backend that stores traces in object storage (S3), eliminating
> the need for a separate Elasticsearch cluster.

### 📘 Concept Explanation

**What it is:**
Jaeger is an open-source distributed tracing platform that collects
spans from all services, stores them in a searchable backend, and
provides a UI for trace visualization and analysis.

**The problem it solves:**
Spans generated by individual services have no use on their own.
They need a central system that: receives spans from all services,
indexes them by trace ID for O(1) lookup, provides search by
service name and time range, and visualizes the span tree as a
Gantt chart for latency analysis.

**How it works:**
Jaeger production architecture:

```
[Service] --> OTel Collector --> Jaeger Collector
                 (sidecar or                |
                  DaemonSet)        [Storage Backend]
                                   Elasticsearch (prod)
                                   Cassandra (alt)
                                   Badger (dev/test)
                                            |
                                   [Jaeger Query]
                                   REST API + UI
                                   Trace search
                                   Gantt visualization
```

> **Diagram walkthrough:** Services export spans to the OTel
> Collector (sidecar handles batching and retry). The Collector
> forwards to Jaeger Collector which writes to the storage backend.
> Jaeger Query serves the UI and API. Separation between Collector
> and Query allows independent scaling of ingestion vs queries.

Key Jaeger UI workflows:

**Trace search:** search by service=checkout, operation=POST /checkout,
min duration=500ms, time range=last 1 hour. Returns a list of
traces matching the criteria. Click any trace to open its Gantt
chart.

**Gantt chart:** horizontal bars showing each span's start time and
duration. Nested indentation shows parent-child relationships.
Color coding by service. Click any span to see its attributes,
events, and logs.

**Compare traces:** select two traces (a fast one and a slow one)
and compare them side-by-side to identify which span differs.

**The key insight:**
Searching by `min duration` is the most powerful Jaeger search
for performance investigation. Filter for traces above your
p99 SLO threshold to find only the slow traces and understand
which span is responsible.

**When to use it:**
Jaeger (or Grafana Tempo as an alternative) for any Kubernetes
environment with microservices. The span data is only valuable
when it has a query layer.

**When NOT to use it:**
Do not run Jaeger with in-memory storage in production: traces
are lost on every restart. Use Elasticsearch or Cassandra as
the storage backend. Do not run Jaeger All-in-One (single binary)
for more than 100,000 spans/day: it is not scalable.

**Alternatives:**
- Grafana Tempo: S3-backed trace storage; no Elasticsearch needed;
  tighter Grafana integration; lower operational cost
- Zipkin: older standard; compatible spans with some Jaeger tooling;
  fewer features
- AWS X-Ray: managed, vendor-specific; no self-hosting; integrates
  with AWS services automatically

**First-principles derivation:**
A distributed trace is a set of spans sharing a trace ID. Querying
"give me the trace for this specific request" requires an index
on trace ID that maps to a storage location. Querying "give me
all slow traces for checkout in the last hour" requires an index
on (service, operation, duration, timestamp). Jaeger's Elasticsearch
storage provides both: a trace ID index for point lookups and
a time-range + field index for search queries.

### 💻 Code Example

**Example 1: BAD - Jaeger Agent (deprecated pattern)**

```yaml
# BAD: Using Jaeger Agent (deprecated in favor of OTel Collector)
# Jaeger Agent is a UDP-based thin client with no retry,
# no persistence, and limited configuration
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: jaeger-agent
spec:
  template:
    spec:
      containers:
        - name: jaeger-agent
          image: jaegertracing/jaeger-agent:1.45
          ports:
            - containerPort: 6831  # UDP - no retry
              protocol: UDP
          args:
            - --reporter.grpc.host-port=jaeger-collector:14250
# Problem: UDP with no persistence or retry
# Span loss on network congestion is silent
# Jaeger recommends replacing with OTel Collector
```

> **Code walkthrough:** The BAD example uses the Jaeger Agent,
> which was the original collection pattern. The Agent uses UDP
> (port 6831) for span reception, which has no acknowledgement,
> no retry, and no persistence. Under network congestion, spans
> are silently dropped. Jaeger's own documentation recommends
> replacing the Jaeger Agent with an OpenTelemetry Collector,
> which uses OTLP over gRPC with retry and backpressure.

**Example 2: GOOD - OTel Collector exporting to Jaeger**

```yaml
# GOOD: OTel Collector with Jaeger export
# Provides retry, batching, and back-pressure handling
apiVersion: opentelemetry.io/v1alpha1
kind: OpenTelemetryCollector
metadata:
  name: otel-collector
spec:
  mode: DaemonSet
  config: |
    receivers:
      otlp:
        protocols:
          grpc:
            endpoint: "0.0.0.0:4317"
          http:
            endpoint: "0.0.0.0:4318"

    processors:
      batch:
        # Send every 5 seconds or 100 spans, whichever first
        timeout: 5s
        send_batch_size: 100

      memory_limiter:
        # Prevent OOM on span burst
        limit_mib: 512
        spike_limit_mib: 128

      tail_sampling:
        decision_wait: 10s
        policies:
          # Always keep errors and slow traces
          - name: error-policy
            type: status_code
            status_code: {status_codes: [ERROR]}
          - name: slow-traces
            type: latency
            latency: {threshold_ms: 500}
          # Sample 1% of healthy traces
          - name: base-rate
            type: probabilistic
            probabilistic: {sampling_percentage: 1}

    exporters:
      otlp/jaeger:
        endpoint: "jaeger-collector:4317"
        tls:
          insecure: false
        retry_on_failure:
          enabled: true
          max_elapsed_time: 300s

    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch, tail_sampling]
          exporters: [otlp/jaeger]
```

> **Code walkthrough:** The GOOD setup uses the OTel Collector
> with three key processors. The batch processor groups spans
> for efficient transmission. The memory_limiter prevents OOM
> on burst traffic. The tail_sampling processor buffers complete
> traces (decision_wait: 10s) and applies sampling policies:
> all ERROR traces and traces above 500ms are kept; 1% of healthy
> traces are sampled. This gives 100% coverage for diagnostic
> cases (errors, slow) while controlling storage cost. The exporter
> uses gRPC with TLS and retry, eliminating the UDP drop problem.

### ⚠️ Common Misconceptions

| Misconception | Reality |
| ------------- | ------- |
| "Jaeger Agent is the recommended collection method" | Jaeger recommends OTel Collector over Jaeger Agent since Jaeger 1.35 (2022). Agent uses UDP with no retry |
| "All-in-One Jaeger is fine for production" | All-in-One uses in-memory storage (lost on restart) and does not scale. Use the production topology with Elasticsearch |
| "Sampling is optional if you have enough storage" | At 10,000 RPS, storing 100% of traces costs terabytes per day. Sampling is required for cost and performance |
| "Jaeger collects traces automatically" | Jaeger only receives what services send to it. Services must be instrumented (OTel SDK) and configured to export to the OTel Collector |

### 🚨 Failure Modes and Diagnosis

**Mode 1 - Traces not appearing in Jaeger**

Symptom: Services are instrumented with OTel but traces do not
appear in Jaeger UI even for requests I just made.

Root cause: One of four common causes - (1) OTel exporter is
not configured with Jaeger endpoint, (2) sampling rate is 0%
(all traces dropped), (3) OTel Collector is not running, (4)
Jaeger storage backend (Elasticsearch) is down.

Diagnostic:
```bash
# Step 1: Check OTel Collector is receiving spans
kubectl logs -n monitoring otel-collector-xxx | \
  grep "traces"
# Look for: "Traces exporter: 100 spans exported"

# Step 2: Check Jaeger Collector is receiving spans
kubectl logs -n monitoring jaeger-collector-xxx | \
  grep "spans"

# Step 3: Check Elasticsearch health
curl http://elasticsearch:9200/_cluster/health | \
  jq .status
# green = healthy, yellow = degraded, red = down

# Step 4: Check sampling is not 0
# In OTel SDK configuration:
# OTEL_TRACES_SAMPLER=parentbased_traceidratio
# OTEL_TRACES_SAMPLER_ARG=1.0  (1.0 = 100%, 0.01 = 1%)
```

Fix: Address whichever step fails. Most common: sampling
environment variable was set to 0.0 in production for cost
control and no one updated it.

Prevention: Health check in CI: after deployment, verify that
at least one trace appears in Jaeger for the service within
60 seconds.

---

**Mode 2 - Jaeger Elasticsearch index size exploding**

Symptom: Elasticsearch disk usage grows 5GB per day and is
now at 80% capacity. Jaeger UI slows down.

Root cause: Trace volume increased (new service added, sampling
rate increased) and Elasticsearch index management policy was
not updated.

Diagnostic:
```bash
# Check index sizes
curl -s http://elasticsearch:9200/_cat/indices/jaeger-span-* \
  --data-urlencode 'v=true&s=store.size:desc' | head -20
# Shows per-day index sizes
# Most recent index shows current ingest rate
```

Fix: Enable index rollover and retention. Jaeger's Elasticsearch
index cleaner job deletes indices older than N days. Reduce
sampling rate for healthy traces.

Prevention: Alert when Elasticsearch disk usage exceeds 70%.
Review Jaeger retention policy when adding new services.

**Q1 [MID] What are the main components of Jaeger's production architecture?**

*Why they ask:* Tests practical Jaeger operations knowledge.

*Likely follow-up:* What changed with Jaeger 1.35 regarding collection?

Jaeger's production architecture has four main components. First,
the Jaeger Collector: receives spans from the OTel Collector (or
directly via OTLP), validates, and writes to the storage backend.
Multiple Collector replicas can run behind a load balancer for HA.
Second, the storage backend: Elasticsearch (primary recommendation)
or Cassandra. Elasticsearch provides rich search; Cassandra provides
high write throughput. Elasticsearch requires 3+ nodes for production.
Jaeger uses an index-per-day scheme in Elasticsearch; old indices
need to be deleted by a curator job. Third, Jaeger Query: serves
the REST API and web UI. Read-only component; can be scaled
horizontally. Fourth, the OTel Collector (replacing the deprecated
Jaeger Agent): runs as a DaemonSet, receives OTLP spans from services,
applies sampling and batching, and exports to the Jaeger Collector.
The OTel Collector is now the recommended collection layer because
it uses GRPC with retry, unlike the UDP-based Jaeger Agent.

*What separates good from great:* Great candidates describe how to
scale the Jaeger Collector by sharding by trace ID modulo N
(consistent hashing) to ensure all spans from a trace land on
the same Collector instance for tail sampling.

**Q2 [SENIOR] How does tail-based sampling work and why is it better than head-based?**

*Why they ask:* Tests deep sampling strategy knowledge.

*Likely follow-up:* What infrastructure is needed for tail-based sampling?

Head-based sampling makes the keep/drop decision at the start
of a request, before any spans are generated. A 1% head-based
sampler keeps 1% of all requests (chosen randomly) from the
first moment the root span is created, and propagates this
decision via the sampling flag in the traceparent header. All
services downstream inherit the sampling decision. This is
computationally cheap (one random number per request) but it
samples errors and slow requests at the same rate as healthy
fast requests - exactly backwards from what you want. Tail-based
sampling buffers all spans for a trace until the root span
completes (decision_wait window: 10-30 seconds), then applies
sampling policies against the complete trace: keep if any span
has ERROR status, keep if total duration > 500ms, keep 0.1% of
everything else. This ensures 100% of interesting traces (errors,
slow) are retained while controlling storage volume. The
infrastructure cost: the OTel Collector must buffer all spans
in memory (or disk) during the decision window, and all spans
from a single trace must reach the same Collector instance
(use consistent hashing by trace ID).

*What separates good from great:* Great candidates describe the
failure mode of tail sampling: if the Collector restarts during
the decision window, all buffered spans for in-flight traces
are lost, and those traces appear incomplete.

**Q3 [MID] How do you search for the trace that caused a specific error?**

*Why they ask:* Tests practical Jaeger usage.

*Likely follow-up:* What search filters do you use?

In Jaeger UI, I use the Search panel with these filters for
incident investigation: Service = checkout (the service reporting
the error), Operation = POST /checkout (the specific endpoint),
Tags = `error=true` (filter to only ERROR-status traces),
Lookback = 15 minutes (narrow time range to the incident window),
Min Duration = 0ms (include all erroring traces regardless of
latency). This returns a list of traces matching the criteria,
typically sorted by start time. I click the most recent trace,
which opens the Gantt chart. I look for spans with red indicators
(ERROR status). I click the erroring span and read its Events
tab (where recordException() data appears): exception type,
message, and stack trace. The stack trace is typically sufficient
to identify the code line causing the error. If it is a slow
trace rather than an error, I change Min Duration to 1000ms
(above SLO) and change Tags to remove error=true. This shows
all slow traces. I compare a slow trace against a fast trace
using Jaeger's Compare feature to identify which span differs.

*What separates good from great:* Great candidates describe
the Jaeger Service Performance Monitoring feature (SPM) that
shows aggregated latency and error rate per operation, bridging
the gap between metrics and traces.

**Q4 [JUNIOR] What is OTLP and why does it matter for Jaeger?**

*Why they ask:* Tests OpenTelemetry interoperability knowledge.

*Likely follow-up:* Can Jaeger receive Zipkin format spans?

OTLP (OpenTelemetry Protocol) is the vendor-neutral wire protocol
for telemetry data (traces, metrics, logs) defined by the
OpenTelemetry project. It uses Protocol Buffers over gRPC (port
4317) or over HTTP (port 4318). OTLP matters for Jaeger because
it is the modern replacement for Jaeger's own binary protocol.
Services instrumented with the OpenTelemetry SDK emit OTLP spans,
and Jaeger Collector accepts OTLP directly (since Jaeger 1.35).
The benefit is vendor neutrality: a service instrumented with
the OTel SDK can export to Jaeger, Grafana Tempo, Zipkin, or
any OTLP-compatible backend without changing any application code.
Switching trace backends is a configuration change in the OTel
Collector exporter, not a code change. Jaeger also accepts Zipkin
format (for backward compatibility) and its own Thrift binary
format. In all new deployments, OTLP is the recommended protocol
because it is maintained by the CNCF OpenTelemetry project and
supported across the entire observability ecosystem.

*What separates good from great:* Great candidates describe how
OTLP also carries metrics and logs (not just traces), and how
a single OTel Collector pipeline can route all three signals
to their respective backends.

**Q5 [SENIOR] When would you choose Grafana Tempo over Jaeger?**

*Why they ask:* Tests architectural decision-making.

*Likely follow-up:* What does Tempo sacrifice compared to Jaeger?

I choose Grafana Tempo over Jaeger when: (1) The team already
uses Grafana and Prometheus for metrics and Loki for logs. Tempo
integrates natively with the Grafana stack: clicking a trace ID
in a Loki log line opens the trace in Tempo automatically.
(2) The team does not want to operate an Elasticsearch cluster.
Tempo stores traces in object storage (S3 or GCS), which is
operationally trivial and cheap. Jaeger with Elasticsearch
requires managing index life cycles, shard counts, and capacity.
(3) Storage cost is a concern. Tempo on S3 at $0.023/GB is
significantly cheaper than Elasticsearch on EBS. Tempo also
compresses traces efficiently. The sacrifice with Tempo is search
flexibility: Jaeger with Elasticsearch supports arbitrary span
attribute searches (find all traces where db.table=orders).
Tempo's search is tag-based: you must have a trace ID or use
TraceQL to query by specific attribute values. For most teams,
tag-based search is sufficient and the operational simplicity
of Tempo is the better trade-off.

*What separates good from great:* Great candidates describe
TraceQL, Tempo's query language for structured span search,
and how it closes the search gap compared to Jaeger.

**Q6 [MID] How do you correlate a Jaeger trace with a Loki log?**

*Why they ask:* Tests multi-signal correlation workflow.

*Likely follow-up:* What Grafana configuration enables one-click correlation?

Log-to-trace correlation requires two things. First, the log line
must contain the trace ID as a named field. With structured logging
and the OTel Java agent, this happens automatically: the agent
injects trace_id into MDC, and the JSON logger includes it in
every log line. Second, Grafana must be configured to recognize
the trace ID field in log lines and create a link to the trace
in Jaeger or Tempo. In Grafana, open the Loki data source settings.
Add a Derived Field with name "Trace", match on regex
`"trace_id":"([a-f0-9]{32})"`, and set the URL to
`http://jaeger:16686/trace/$${__value.raw}`. After this, every
log line in Grafana's Loki panel shows a clickable icon next to
the trace_id value. Clicking it opens the Jaeger trace in a
new tab. This is the core workflow for incident investigation:
find the error log in Loki, click the trace ID, open the full
trace in Jaeger to see which service caused the error.

*What separates good from great:* Great candidates describe the
reverse correlation: opening a Jaeger trace and seeing the
associated log lines from Loki embedded in the trace UI using
Grafana Explore Links.

**Q7 [JUNIOR] What is sampling and why is 100% trace retention not practical?**

*Why they ask:* Tests fundamental trace economics understanding.

*Likely follow-up:* What percentage do you typically sample in production?

At 10,000 requests per second, 100% trace retention means
collecting, transmitting, and storing 864 million traces per day.
A typical trace for a checkout request with 20 spans is approximately
5-10KB of compressed data. At 10KB per trace: 864M * 10KB = 8.6TB
per day. Elasticsearch at 3 nodes handles approximately 1-2TB/day
before you need more nodes. The cost is also significant: 8.6TB
at $0.10/GB-month (EBS) is $860/month for just 1 day of data.
Sampling reduces this to a manageable volume by retaining only
a representative subset of traces. A typical production sampling
policy: 100% of ERROR traces (you always want error traces for
diagnosis), 100% of traces above your p99 SLO threshold (the
traces most relevant for performance work), and 0.1-1% of healthy
fast traces (enough to validate system behavior). At 10,000 RPS
with 1% error rate: 100 errors/second * 100% = 100 error traces/sec.
9,900 healthy traces * 1% = 99 sampled/sec. Total: ~200 traces/sec.
At 10KB each: 200 * 10KB = 2MB/sec = 173GB/day. Manageable.

*What separates good from great:* Great candidates explain why
you always want to keep 100% of error traces even at high RPS:
the absolute number of errors may be low (1% error rate at 100 RPS
= 1 error/sec), and each error trace has unique diagnostic value.

**Q8 [SENIOR] How do you handle trace context propagation across async message queues?**

*Why they ask:* Tests async tracing knowledge.

*Likely follow-up:* What if the consumer framework does not support OTel?

Trace context propagation across message queues requires explicitly
passing the traceparent header in the message metadata. When service
A publishes a Kafka message, it must inject the current span context
as a message header. When service B consumes the message, it must
extract the header and create a child span. With the OTel Java agent
and OTel-instrumented Kafka client (kafka-clients 3.0+ with OTel
Kafka instrumentation), this is automatic: the agent instruments
KafkaProducer to inject traceparent and KafkaConsumer to extract
it. For unsupported Kafka clients, manual injection:

```java
// Producer side: inject trace context into message header
Headers headers = new RecordHeaders();
GlobalOpenTelemetry.getPropagators()
    .getTextMapPropagator()
    .inject(Context.current(), headers,
        (h, key, value) ->
            h.add(key, value.getBytes()));
ProducerRecord<String, Order> record =
    new ProducerRecord<>("orders", null, order, headers);
producer.send(record);
// Consumer side: extract and create child span
Context ctx = GlobalOpenTelemetry.getPropagators()
    .getTextMapPropagator()
    .extract(Context.current(), record.headers(),
        (h, key) -> {
          Header header = h.lastHeader(key);
          return header != null
            ? new String(header.value())
            : null;
        });
Span span = tracer.spanBuilder("order.process")
    .setParent(ctx).startSpan();
```

> **Code walkthrough:** The producer injects the current trace
> context into Kafka headers using OTel's TextMapPropagator, which
> handles the W3C Trace Context header format. The consumer extracts
> it back into a Context object. Creating the child span with
> setParent(ctx) links the consumer span to the original producer
> trace, creating a continuous trace across the async boundary.

*What separates good from great:* Great candidates describe the
"link" relationship for fire-and-forget messages where connecting
the consumer to the producer trace is useful but the consumer
should not appear as a child of the producer (use span.addLink()
instead of setParent).

**Q9 [STAFF] How do you design trace sampling for a 50,000 RPS system?**

*Why they ask:* Tests production-scale trace management.

*Likely follow-up:* What is the infrastructure cost of your sampling strategy?

For a 50,000 RPS system, tail-based sampling in the OTel Collector
is required. The sampling policy: 100% of ERROR spans (a 1% error
rate at 50,000 RPS = 500 errors/sec; each trace is 5-10KB; 500
* 10KB = 5MB/sec = 432GB/day - large but important to retain).
100% of traces with duration > p99 SLO threshold (e.g., > 500ms).
Assuming 1% of traces are slow: 500 slow traces/sec * 10KB = 5MB/sec.
0.01% of healthy fast traces: 50,000 * 0.98 * 0.0001 = 5 healthy/sec.
Total: ~1,005 traces/sec * 10KB = 10MB/sec = 864GB/day. This requires
a Grafana Tempo or Jaeger instance with approximately 1TB/day
throughput. Infrastructure: Grafana Tempo on S3 (write path:
5 Tempo distributor pods, 10 Tempo ingester pods). The tail sampling

# Correlation IDs and Request Context

**TL;DR** - A correlation ID is a unique identifier propagated
across all services for a single user request, enabling log
search to find all events for that request. Correlation IDs are
the lightweight alternative to full distributed tracing when
traces are unavailable or too expensive.

---

### 🎯 Model Answer

**30 seconds:**

> incoming request, then propagated in every outbound call's headers
> and included in every log line. If a user reports "my order failed,"
> the support team gives you the correlation ID from the error
> response. You search all service logs for that ID and find every

> full tracing but less powerful.

**3 minutes (Senior):**

> most teams already have) rather than a full distributed trace

> traces are complementary, not alternatives. When you have both:
> every log line contains both the correlation_id (human-generated
> or user-visible, e.g., the checkout reference number) and the

> calls (HTTP header, message metadata), and inject it into the
> logging context (MDC) for all log lines on that request thread.

> for log search.

### 📘 Concept Explanation

**What it is:**
A correlation ID is a unique identifier assigned at request entry
and propagated across all service boundaries, included in every
log line for that request, enabling log search to retrieve all
events for a specific request.

**The problem it solves:**
In a distributed system without tracing, a user reports "my
checkout failed 10 minutes ago." The relevant log events are
spread across the checkout service, payment service, inventory
service, and order service. Without a common identifier, finding
them requires searching each service's logs by time range and
user ID - slow, error-prone, and incomplete. With a correlation
ID, one search `{correlation_id="req-8f2a1c9e"}` across all
services returns every event for that request.

**How it works:**
Correlation ID lifecycle:

```
User Request
    |
[API Gateway]
  - Checks X-Request-ID header (client-provided)
  - OR generates UUID: "req-8f2a1c9e"
  - Sets MDC: correlation_id = "req-8f2a1c9e"
    |
[Service A - checkout]
  - Extracts X-Request-ID from inbound header
  - Sets MDC: correlation_id = "req-8f2a1c9e"
  - ALL log lines include correlation_id automatically
  - Passes header to all outbound calls:
      X-Request-ID: req-8f2a1c9e
    |
[Service B - payment]
  - Extracts X-Request-ID from inbound header
  - Sets MDC: correlation_id = "req-8f2a1c9e"
  - ALL log lines include correlation_id automatically
    |
Error Response to User:
  - Response body: {"error": "...",
                    "requestId": "req-8f2a1c9e"}
  - Header: X-Request-ID: req-8f2a1c9e
```

**The key insight:**
Returning the correlation ID in the error response is critical
for support use cases. When a user calls support and says "I got
an error," support asks "what was the request ID in the error
message?" and uses it to search logs across all services. Without
the ID in the error response, the ID serves only for internal
investigation (if you already have the ID from another source).

**When to use it:**
Every HTTP service should propagate a request ID header. Even
when full distributed tracing is deployed, correlation IDs remain
useful for: support team investigations using human-readable IDs,
linking internal trace IDs to user-visible reference numbers,
and log search without the Jaeger UI.

**When NOT to use it:**
Do not generate a new correlation ID for each service-to-service
call within a request. The correlation ID must be the SAME value
throughout the entire request lifecycle, from entry point to
final response. Generating new IDs at each hop breaks the search.

**Alternatives:**
- W3C Trace Context (trace_id): the OTel trace ID serves the same
  purpose and is more powerful (links to Jaeger). Use trace_id
  as the primary correlation ID when OTel is deployed.
- Business reference numbers: order ID, session ID, transaction ID
  provide human-meaningful correlation. Include these alongside
  the technical request ID.

**First-principles derivation:**
Log search in a distributed system is a join operation: find all
log lines where request = X across N service log streams. A join
requires a common key. The correlation ID is that key. Without
it, the join must use time range + user ID + service name, which
is imprecise (a user may have multiple concurrent requests) and
slow (full scan). With a correlation ID, the join is an exact
match on an indexed field.

### 💻 Code Example

**Example 1: BAD - No correlation ID propagation**

```java
// BAD: correlation ID extracted but not propagated
@GetMapping("/checkout")
public ResponseEntity<Order> checkout(
    HttpServletRequest request,
    @RequestBody CartRequest req) {

    // Extract header - but NEVER use it
    String requestId = request.getHeader("X-Request-ID");
    // requestId is null or present but unused

    // Calls payment service WITHOUT passing request ID
    paymentClient.capture(req.getPayment()); // NO HEADER

    log.info("Checkout completed for user: {}",
        req.getUserId());
    // Log has no requestId - cannot search by request
    return ResponseEntity.ok(order);
}
// During incident: "Find logs for requestId X-123"
// Impossible: requestId never injected into logs
// PaymentService never received the requestId
```

> **Code walkthrough:** The BAD example extracts the X-Request-ID
> header but does nothing with it. The downstream call to payment
> service does not include the header, so payment service logs
> cannot be correlated to checkout logs. The log statement does
> not include request_id, so searching by request ID across logs
> returns zero results. The correlation ID header exists but provides
> zero value because it was never injected into the logging context
> or propagated downstream.

**Example 2: GOOD - Correlation ID filter + MDC injection**

```java
// GOOD: Servlet Filter injects correlation ID into MDC
// for all requests automatically
@Component
@Order(1)  // Must run before other filters
public class CorrelationIdFilter
    extends OncePerRequestFilter {

    private static final String REQUEST_ID_HEADER =
        "X-Request-ID";
    private static final String MDC_KEY =
        "correlation_id";

    @Override
    protected void doFilterInternal(
        HttpServletRequest req,
        HttpServletResponse res,
        FilterChain chain)
        throws ServletException, IOException {

        // Use client-provided ID or generate new one
        String correlationId = Optional.ofNullable(
            req.getHeader(REQUEST_ID_HEADER))
            // Validate format to prevent log injection
            .filter(id -> id.matches("[a-zA-Z0-9-]{8,64}"))
            .orElseGet(() ->
                "req-" + UUID.randomUUID()
                    .toString().replace("-","").substring(0,16)
            );

        // Inject into MDC - all subsequent log lines
        // on this thread automatically include it
        MDC.put(MDC_KEY, correlationId);

        // Return it in the response header
        res.setHeader(REQUEST_ID_HEADER, correlationId);

        try {
            chain.doFilter(req, res);
        } finally {
            // CRITICAL: clear MDC after request
            // to prevent leaking between requests
            // in thread pool environments
            MDC.remove(MDC_KEY);
        }
    }
}

// HTTP client configuration: propagate to downstream
@Bean
public RestTemplate correlatingRestTemplate(
    ObjectProvider<CorrelationIdInterceptor> interceptors) {
    RestTemplate rt = new RestTemplate();
    rt.setInterceptors(List.of(new ClientHttpRequestInterceptor() {
        @Override
        public ClientHttpResponse intercept(
            HttpRequest req, byte[] body,
            ClientHttpRequestExecution exec)
            throws IOException {
            // Propagate correlation ID to downstream service
            String cid = MDC.get("correlation_id");
            if (cid != null) {
                req.getHeaders()
                    .set("X-Request-ID", cid);
            }
            return exec.execute(req, body);
        }
    }));
    return rt;
}
```

> **Code walkthrough:** The GOOD example uses a Servlet filter to
> handle correlation ID lifecycle at the framework level. The filter
> accepts a client-provided ID (with format validation to prevent
> log injection attacks) or generates a new one. The MDC injection
> means that all log statements on the request thread automatically
> include correlation_id without any changes to log call sites.
> The response header returns the ID to the caller. The finally
> block clears MDC to prevent the correlation ID from leaking
> to subsequent requests in a thread pool. The RestTemplate
> interceptor propagates the MDC value to all downstream HTTP calls.

### ⚠️ Common Misconceptions

| Misconception | Reality |
| ------------- | ------- |
| "Correlation IDs replace distributed traces" | Correlation IDs provide log correlation. Distributed traces provide timing relationships and critical path analysis. Both are needed |

### 🚨 Failure Modes and Diagnosis

**Mode 1 - Correlation ID not in downstream logs**

Symptom: Searching by correlation ID in Loki returns logs from
the API gateway and checkout service but not from the payment
service.

Root cause: Payment service is not extracting the X-Request-ID
header from inbound requests. Its logs include no correlation_id
field.

Diagnostic:
```bash
# Check if payment service logs include correlation_id
{app="payment"} | json | correlation_id != ""
# If no results, payment service is not setting MDC

# Check if the header is reaching payment service
{app="payment"} | json | level="DEBUG" |
  line_format "{{.http_request_headers}}"
# Look for X-Request-ID in the request headers
```

Fix: Add the correlation ID filter to the payment service.
If it is a different language, implement equivalent MDC
injection for that language's logging framework.

Prevention: Integration test that makes an end-to-end checkout
request and verifies that correlation_id appears in logs from
every service in the call chain.

---

**Mode 2 - Log injection via malicious correlation ID**

Symptom: Log analysis shows unusual log lines with embedded
newlines, or alerts fire for ERROR log lines that contain
no stack trace.

Root cause: A client sent an X-Request-ID header containing
embedded newline characters followed by a crafted log line:
`req-1234\nERROR: Fake error injected`

Root cause: The correlation ID filter accepts any value without
validation and injects it directly into the log.

Diagnostic:
```bash
# Search for correlation IDs containing newlines
{app="checkout"} | json | correlation_id =~ ".*\n.*"
# Or look for log lines missing standard fields
# (injected lines may not have service/trace_id fields)
```

Fix: Add format validation before MDC injection:
`id.matches("[a-zA-Z0-9-]{8,64}")` - reject IDs
containing special characters, newlines, or log-format
delimiters.

Prevention: Security review of any filter that injects
external input into log output.

**Q1 [MID] How does a correlation ID enable distributed log search?**

*Why they ask:* Tests understanding of the core value proposition.

*Likely follow-up:* What are the requirements for effective correlation?

A correlation ID enables distributed log search by providing a
common indexed field across all service log streams. Without a
common field, finding all log events for a specific user request
requires searching each service's logs by time range and user ID
- time range is imprecise (many requests in any given second),
user ID may match multiple concurrent requests. With a correlation
ID, the search is: `{correlation_id="req-8f2a1c9e"}` in Loki
or Elasticsearch, returning every log line from every service
that handled this request. Three requirements for this to work.
First, the same ID must be used across all services (no regenerating
at each hop). Second, the ID must be injected into the logging
MDC for all log lines on the request thread (not just the entry
and exit log lines). Third, all service logs must be in the same
log aggregation system with consistent field names. If checkout
logs use `correlationId` and payment logs use `requestId`, the
cross-service search requires two separate queries and a manual
join.

*What separates good from great:* Great candidates describe the
log field name standardization requirement and how they enforce
it across services.

**Q2 [JUNIOR] Where should correlation IDs be generated?**

*Why they ask:* Tests understanding of the entry point pattern.

*Likely follow-up:* What happens if you generate a new one at each service?

Correlation IDs should be generated at the entry point of the
system - the API gateway or the first service that receives the
external request. If a client provides an X-Request-ID header
with a valid format, accept it (this allows clients to include
their own reference in server logs). If no header is provided,
generate a new UUID. From that point, the same ID must be
propagated to every downstream service. If you generate a new
correlation ID at each service, you have N isolated IDs where
N is the number of services, and searching by any one ID finds
only that service's logs. The correlation across services is
lost. The API gateway is the natural generation point because
it is the boundary between external and internal traffic. In
a Kubernetes cluster, an ingress controller (NGINX Ingress,
Kong) can be configured to generate and inject the correlation
ID header automatically before the request reaches any service,
so all services receive a pre-populated ID without any service
needing to generate one.

*What separates good from great:* Great candidates describe the
NGINX Ingress configuration for injecting X-Request-ID:
`nginx.ingress.kubernetes.io/configuration-snippet: "more_set_headers 'X-Request-ID: $request_id';"`.

**Q3 [SENIOR] How do you correlate across synchronous and asynchronous service calls?**

*Why they ask:* Tests async context propagation knowledge.

*Likely follow-up:* What happens to MDC when you use CompletableFuture?

Synchronous correlation is straightforward: the MDC value is
available on the request thread and the HTTP client interceptor
copies it to the outbound header. Asynchronous correlation requires
explicit context propagation. MDC is thread-local: when you submit
work to an executor via CompletableFuture.supplyAsync() or a
TaskExecutor, the worker thread does not inherit the parent
thread's MDC. Fix: copy MDC before submitting and restore it
in the worker. Spring's TaskDecorator provides a clean mechanism:
configure your TaskExecutor with a decorator that copies the
MDC snapshot from the submitting thread and restores it in the
worker thread. For Kafka: include the correlation_id as a Kafka
message header when publishing. The consumer extracts the header
and injects it into MDC before processing the message. For fire-
and-forget async operations where there is no response to
correlate: use a span link rather than parent-child relationship.
The async operation gets its own correlation ID but includes a
reference to the originating request's correlation ID in an
explicit link field.

*What separates good from great:* Great candidates provide
the specific Spring TaskDecorator implementation that copies
and restores MDC for async tasks.

**Q4 [JUNIOR] Why must you validate correlation ID format before MDC injection?**

*Why they ask:* Tests security-conscious coding.

*Likely follow-up:* What is log injection and how does it affect correlation IDs?

Correlation ID injection is a log injection attack vector. The
correlation ID is passed by the client in the X-Request-ID header.
Without format validation, a malicious client can craft a header
value like: `legit-id\nERROR: Admin credentials leaked: admin/Admin123`
When this value is injected into the MDC and appears in a log
line formatted as key=value or JSON, it may insert a second log
line (the attacker's fake error line) into the log stream. In
JSON logging, a newline in an MDC field terminates the JSON object
and starts a new, malformed or crafted log line. This can cause
false alerts (fake ERROR lines), corrupt log parsing, or, in
extreme cases, mislead incident responders. Validation rule:
the correlation ID must match `[a-zA-Z0-9\-_]{8,64}` (alphanumeric
with hyphens and underscores, 8 to 64 characters). Reject any
value outside this pattern and generate a new ID instead.
The fix is a one-line regex check in the correlation ID filter
before calling MDC.put().

*What separates good from great:* Great candidates describe how
JSON-format logging provides better protection than key=value
format because embedded newlines in a JSON field value are escaped
to `\n` and do not terminate the JSON object.

**Q5 [SENIOR] How do correlation IDs interact with distributed traces when both are present?**

*Why they ask:* Tests understanding of multi-ID environments.

*Likely follow-up:* Should you return the trace ID in error responses?

When both are present, they serve different audiences. The trace
ID (128-bit OTel trace ID, 32 hex characters) is for engineering
investigation: paste it into Jaeger and open the full trace.
The correlation ID is for support investigation: shorter (16-20
characters), included in error responses, and used by support
teams to search logs. The structured log entry should include
both: `trace_id=4bf92f3577b34da6a3ce929d0e0e4736` and
`correlation_id=req-8f2a1c9e`. In practice, I use the trace ID
as the correlation ID when OTel is deployed: configure MDC to
use `trace_id` (injected by OTel agent) as the searchable field.
The correlation ID filter still runs to generate a shorter
`request_id` for user-visible error responses. The log line
has three identifiers: `trace_id` (OTel trace, 32 chars),
`request_id` (correlation, 20 chars, in error responses),
and `order_id` (business reference, in order-related logs).
I do NOT return the trace_id in error responses: it is an
internal implementation detail that exposes the observability
stack topology to clients.

*What separates good from great:* Great candidates describe the
security rationale for not returning trace IDs: an attacker
who knows trace IDs can potentially query your trace store
directly if it is not properly secured.

**Q6 [MID] What is the difference between X-Request-ID and X-Correlation-ID headers?**

*Why they ask:* Tests knowledge of header conventions.

*Likely follow-up:* Which should you use in a new service?

X-Request-ID and X-Correlation-ID are both non-standard HTTP
headers used for the same purpose: propagating a request
identifier across services. X-Request-ID is the more common
convention, used by NGINX, AWS Application Load Balancer, and
many framework auto-instrumentation tools. X-Correlation-ID is
more commonly used in enterprise environments and is the header
name in Azure's API Management. There is no technical difference:
both contain a string identifier that should be propagated unchanged
through all service hops. For a new service, I recommend X-Request-ID
because it is more widely supported by infrastructure components
(NGINX Ingress can auto-generate it) and is the default in
Spring Cloud Sleuth and OpenTelemetry trace context injection.
Consistency within an organization matters more than which name
you choose: if half your services use X-Request-ID and half use
X-Correlation-ID, log search requires two fields. The W3C Trace
Context traceparent header is the modern standard that supersedes
both for trace propagation, but X-Request-ID remains useful
as the human-readable support-facing identifier.

*What separates good from great:* Great candidates describe their
organization's header naming standard and how they enforce it
across services.

**Q7 [STAFF] How do you include correlation IDs in asynchronous message streams?**

*Why they ask:* Tests async propagation design thinking.

*Likely follow-up:* How do you correlate a Kafka message with its originating HTTP request?

For Kafka messages, correlation IDs must be included as message
headers. When service A publishes a message to Kafka during
request handling, it reads the current correlation_id from MDC
and writes it as a Kafka header. When service B consumes the
message, it extracts the header and injects it into MDC before
any log statements execute. This ensures that all log lines
from the consumer processing are searchable with the original
request's correlation ID. The complete design: message header
`X-Correlation-ID: req-8f2a1c9e`, consumer filter that extracts
this header and calls `MDC.put("correlation_id", headerValue)`.
For a fan-out pattern (one request generates multiple messages):
each message carries the same correlation ID. All consumer instances
processing those messages include the same ID in their logs.
Searching for the correlation ID finds all consumer processing
across all instances. For sequential chaining (A publishes to
Kafka, B consumes and publishes to another topic, C consumes):
each service passes the correlation_id header forward, so the
chain appears as a single correlated unit in log search.

*What separates good from great:* Great candidates describe
the cleanup concern for consumer MDC: if a consumer processes
multiple messages sequentially on the same thread, the MDC
must be cleared and reset for each message to prevent ID leakage
between messages.

**Q8 [SENIOR] How do you handle correlation when a request fails and is retried?**

*Why they ask:* Tests retry correlation design.

*Likely follow-up:* What is the right behavior for idempotency keys?

Retry correlation has two competing concerns. On one hand,
you want to correlate the retry with the original request
(same user, same operation). On the other hand, each retry
is a distinct request that may have different behavior (it
may succeed where the original failed). My approach: preserve
the original correlation ID across retries. When the client
retries with the same X-Request-ID header, the server recognizes
it as a retry of the same logical request. All log lines for
all attempts are searchable with the same ID. The server may
add a retry counter as a separate log field: `retry_attempt=2`.
For idempotency keys (separate from correlation IDs): the
idempotency key enables the server to detect duplicate requests
and return the cached result without re-processing. The
idempotency key is usually a client-generated UUID that the
client holds constant across retries. It is distinct from the
correlation ID: the correlation ID is for log search; the
idempotency key is for deduplication. In log lines, include
both: `correlation_id=req-8f2a1c9e idempotency_key=idem-3f7a2b1c
retry_attempt=2`.

*What separates good from great:* Great candidates describe
the interaction between retry correlation and distributed traces:
each retry attempt should be a separate trace (different trace_id)
linked to the original via a span link, while sharing the same
correlation_id.

**Q9 [JUNIOR] Should you include the correlation ID in successful response bodies?**

*Why they ask:* Tests practical API design judgment.

*Likely follow-up:* What about in 4xx error responses?

The correlation ID should appear in the response header
(X-Request-ID) for all responses, both successful and error.
This allows clients to log it for debugging. In the response
body: include it only in error responses, not in successful
responses. Successful response bodies should contain business
data (the order, the payment confirmation, the search results).
Adding infrastructure metadata (request IDs) to successful
responses pollutes the business data structure and may
confuse API consumers. In error response bodies, include
the request_id because it enables users to provide it to
support: `{"error": "Payment declined", "requestId": "req-8f2a1c9e",
"timestamp": "2026-05-29T14:32:05Z"}`. This is the pattern
recommended by major API providers (Stripe, Twilio) and is
what users and support teams need. The response header approach
for successful responses is correct because clients can log
the header for their own debugging without it appearing in
their UI or business logic.

*What separates good from great:* Great candidates describe
the error response schema standard they would define for
the organization, ensuring all services return the same error
format with the request ID.
