# Quarkus in Kubernetes Microservices

**Interview Weight:** hard - Architecture is the Staff/Principal
differentiator. Tested for system-level design decisions.

---

### 🎯 Model Answer

**30 seconds:**

> Quarkus is purpose-built for Kubernetes: fast startup
> enables pre-emption and autoscaling, low memory enables
> higher pod density, native image eliminates JVM overhead
> for sidecar containers. quarkus-kubernetes extension
> generates Kubernetes YAML. quarkus-smallrye-health
> provides readiness/liveness probes. OpenTelemetry
> for distributed tracing across services. OIDC for
> JWT-based service identity.

**3 minutes (Senior):**

> Kubernetes-native features:
>
> Quarkus-kubernetes extension:
>   Generates Deployment, Service, ConfigMap YAML.
>   Auto-configures: readiness (/q/health/ready),
>     liveness (/q/health/live), ports, labels.
>   quarkus.kubernetes.replicas=3
>   quarkus.kubernetes.resources.requests.memory=256Mi
>   quarkus.kubernetes.ingress.expose=true
>
> Health probes:
>   @Liveness: is the app alive? OOMKilled = fail.
>   @Readiness: is it ready for traffic?
>     DB connected? Cache warmed?
>   @Startup: used for slow-start apps.
>   quarkus-smallrye-health: implements all three.
>
> Autoscaling considerations:
>   HPA (Horizontal Pod Autoscaler) on CPU or
>     custom metrics (Kafka lag, request rate).
>   Fast Quarkus startup: new pods ready in <5s.
>   For Spring: pod takes 30s → slow scale-out.
>   quarkus.kubernetes.hpa.*: configure HPA.
>
> Service discovery:
>   Kubernetes Service DNS (default).
>   Stork (SmallRye Stork): load balancing.
>   RestClient with @RegisterRestClient:
>     auto-discovers by service name.
>
> Configuration:
>   ConfigMap → application.properties override.
>   Secret → password env vars.
>   quarkus.kubernetes.config-map=app-config.

**Blank Mind Recovery:**

**(1) Restate:** "You are asking about how Quarkus
fits into Kubernetes microservices architecture."

**(2) First principles:** "Kubernetes manages containers.
Containers need: fast startup, health endpoints,
externalized config, observability."

**(3) Bridge:** "Quarkus is designed to check all
Kubernetes requirements by default. Other frameworks
retrofitted Kubernetes support; Quarkus started there."

### 💻 Code Example

```java
// Health endpoints
@ApplicationScoped
public class DatabaseHealthCheck
        implements HealthCheck {

    @Inject
    DataSource dataSource;

    @Liveness  // Liveness probe: is app alive?
    @Override
    public HealthCheckResponse call() {
        // Quick check: can we reach the pool?
        try {
            if (dataSource.getConnection()
                    .isValid(1)) {
                return HealthCheckResponse
                    .named("database")
                    .up()
                    .build();
            }
        } catch (Exception e) {
            return HealthCheckResponse
                .named("database")
                .down()
                .withData("error", e.getMessage())
                .build();
        }
        return HealthCheckResponse
            .named("database")
            .down()
            .build();
    }
}

@ApplicationScoped
public class ReadinessCheck
        implements HealthCheck {

    @Inject
    CacheWarmer cacheWarmer;

    @Readiness  // Readiness: ready for traffic?
    @Override
    public HealthCheckResponse call() {
        if (!cacheWarmer.isWarmed()) {
            return HealthCheckResponse
                .named("readiness")
                .down()
                .withData("reason", "cache not warmed")
                .build();
        }
        return HealthCheckResponse
            .named("readiness")
            .up()
            .build();
    }
}
```

> **Code walkthrough:** @Liveness and @Readiness annotate
> HealthCheck implementations. Quarkus registers them
> at /q/health/live and /q/health/ready. The liveness
> probe checks if the DB connection is valid (1-second
> timeout - fast check). The readiness probe checks
> whether the cache is warmed - if not, Kubernetes withholds
> traffic until the app is ready. The quarkus-kubernetes
> extension generates the complete Deployment YAML from
> application.properties, including probe configuration.

**[STAFF] Q1 - How does Quarkus startup speed
change Kubernetes autoscaling strategy?**

*Why they ask:* Architectural impact of fast startup.

Traditional (Spring, ~30s startup):
- Set scale trigger at 50% CPU
- Buffer: 50% headroom for scale-up delay
- Minimum replicas: high (slow scale-in too)
- Cost: over-provisioned by design

Quarkus (5s JVM, 100ms native):
- Set scale trigger at 70-80% CPU
- New pod ready in <5s, traffic shifted in <10s
- Can scale to minimum replicas in off-peak (fast scale-up when needed)
- Cost: 20-30% reduction in steady-state compute

HPA configuration comparison:
```yaml
# Spring: conservative triggers
spec:
  minReplicas: 5     # Can't scale in: too slow
  maxReplicas: 20
  targetCPUUtilizationPercentage: 50  # Early trigger

# Quarkus: aggressive triggers
spec:
  minReplicas: 2     # Scale in safely: fast scale-out
  maxReplicas: 20
  targetCPUUtilizationPercentage: 75  # Later trigger
  scaleDown:
    stabilizationWindowSeconds: 60   # Scale in faster
```

> **Code walkthrough:** This example demonstrates the core pattern in action. The key mechanism shows how the concept works in practice. Study the structure to understand the essential behavior and common usage.

Native image adds the serverless benefit: FaaS cold start
is <100ms. Spring cold start in Lambda is 10-30 seconds
(often unusable without provisioned concurrency).

*What separates good from great:* Quantifying the business
impact: reduced minimum replicas + aggressive triggers
= measurable cost reduction.

# Quarkus Serverless Architecture

**Interview Weight:** high - Serverless is a growing
deployment pattern. Tested for cloud-native roles.

---

### 🎯 Model Answer

**30 seconds:**

> Quarkus supports serverless deployment via AWS Lambda
> (quarkus-amazon-lambda), Azure Functions, and Google
> Cloud Functions. For Lambda: extend QuarkusRequestHandler<Input,Output>.
> Native image is recommended for Lambda: cold start <100ms
> vs JVM cold start 5-15 seconds. Quarkus handles the
> Lambda runtime lifecycle, CDI context per invocation,
> and serialization.

**3 minutes (Senior):**

> Lambda patterns:
>
> Simple handler:
>   Extend RequestHandler<Input, Output>.
>   No HTTP: Lambda event → Java object → result.
>   Quarkus CDI: @Inject works in handler.
>
> HTTP handler (API Gateway):
>   Extend QuarkusRequestHandler<APIGatewayV2HTTPEvent,
>     APIGatewayV2HTTPResponse>.
>   Or: use quarkus-amazon-lambda-http.
>     Maps HTTP requests to JAX-RS resources.
>     Existing @Path controllers work in Lambda.
>
> Native Lambda build:
>   quarkus.native.container-build=true (Linux binary)
>   quarkus-amazon-lambda: build includes Lambda bootstrap.
>   Upload zip: bootstrap + function zip.
>
> Cold start optimization:
>   JVM mode: 5-15s cold start (Provisioned Concurrency).
>   Native mode: 50-100ms (cold start is acceptable).
>   For native: no Provisioned Concurrency needed.
>
> Knative (Kubernetes Serverless):
>   quarkus-kubernetes extension works with Knative.
>   Scale to zero: pod destroyed when no requests.
>   Scale from zero: Quarkus starts in <1s for JVM,
>     <100ms for native.
>
> Cost model:
>   Lambda: pay per invocation + duration.
>   Native: less duration (faster processing) = lower cost.
>   Knative: no pod = no compute cost.

**Blank Mind Recovery:**

**(1) Restate:** "You are asking about deploying Quarkus
as a serverless function."

**(2) First principles:** "Serverless = no always-on server.
Pay only when code runs. Cold start = startup on first invocation."

**(3) Bridge:** "Quarkus for Lambda is like Spring Cloud
Function but with native image for acceptable cold start."

### 💻 Code Example

```java
// Lambda handler: simple event
@Named("orderProcessor")
public class OrderLambdaHandler
        extends RequestHandler<OrderEvent, OrderResult> {

    @Inject
    OrderService orderService;

    @Override
    public OrderResult handleRequest(
            OrderEvent event,
            Context context) {
        try {
            Order order =
                orderService.process(event);
            return OrderResult.success(
                order.getId());
        } catch (Exception e) {
            context.getLogger()
                .log("Error: " + e.getMessage());
            return OrderResult.failure(
                e.getMessage());
        }
    }
}

// Lambda handler: HTTP via API Gateway
@Named("orderApi")
public class OrderApiHandler
        extends QuarkusRequestHandler<
            APIGatewayV2HTTPEvent,
            APIGatewayV2HTTPResponse> {

    // Delegates to JAX-RS resources
    // Existing @Path controllers work without change
}

// Or: use existing JAX-RS controllers with lambda-http
// Just add quarkus-amazon-lambda-http dependency
// Your @Path resources work in Lambda automatically
@Path("/orders")
public class OrderResource {
    // Works in both HTTP server and Lambda mode
    // No code change needed
    @GET
    @Path("/{id}")
    public OrderDto findById(
            @PathParam("id") Long id) {
        return orderService.findById(id);
    }
}
```

```bash
# Native Lambda build
./mvnw package -Pnative \
  -Dquarkus.native.container-build=true

# Creates: target/function.zip
# Contains: bootstrap (native binary) + handler

# Deploy with SAM/CDK
aws lambda create-function \
  --runtime provided.al2 \
  --function-name order-processor \
  --zip-file fileb://target/function.zip \
  --handler not.used \
  --role arn:aws:iam::xxx:role/lambda-role

# Cold start test
time aws lambda invoke \
  --function-name order-processor \
  --payload '{"orderId": 1}' \
  response.json
# Duration: 80ms (native) vs 10s (JVM, first invoke)
```

> **Code walkthrough:** OrderLambdaHandler extends RequestHandler
> and uses @Inject for CDI beans - Quarkus CDI context
> is active per invocation. The HTTP handler (QuarkusRequestHandler)
> maps API Gateway events to JAX-RS requests - existing
> @Path controllers work without modification. The native
> build with container-build creates a Linux binary suitable
> for provided.al2 Lambda runtime. Cold start: 80ms native
> vs 10s JVM.

**[STAFF] Q1 - When should you NOT use serverless
for a Quarkus service?**

*Why they ask:* Decision framework.

Serverless anti-patterns:

1. High sustained throughput (>100 RPS steady state):
   Lambda per-invocation cost > container cost.
   At 100 RPS: 8.6M invocations/day.
   Lambda: $0.20/million = $1.72/day per 100 RPS.
   ECS/K8s: 1 pod = $0.03/hour = $0.72/day.
   Break-even: ~10 RPS.

2. Long-running operations (>15 minutes):
   Lambda max timeout: 15 minutes.
   Use Step Functions or ECS tasks instead.

3. Stateful operations requiring sticky sessions:
   Lambda: stateless by design.
   Stateful: use ECS or Kubernetes with sticky sessions.

4. Require complex networking (VPC peering, NAT):
   Lambda in VPC has additional cold start delay.
   Complex network setup: ECS easier to manage.

5. Large binary or dependencies (>50MB zip):
   Lambda cold start increases with binary size.
   Use Lambda layers or container image if binary large.

When serverless IS right:
- Sporadic processing (webhooks, file uploads)
- Batch jobs (run on schedule)
- Event-driven microservices (Kafka consumer offload)
- Test/dev environments (scale to zero)

*What separates good from great:* Break-even calculation.

| Bar Raiser | Serverless decision framework, cost modeling. |
| Peer Engineer | "Calculated break-even at 15 RPS. Below that: Lambda. Above: ECS. Saved $2,000/month by moving high-traffic services to ECS." |

# Quarkus Migration Strategy from Spring

**Interview Weight:** hard - Migration is a common
real-world decision. Tested for pragmatic thinking.

---

### 🎯 Model Answer

**30 seconds:**

> Migrating from Spring to Quarkus: annotation mapping
> (@Component → @ApplicationScoped, @Autowired → @Inject,
> @GetMapping → @GET + @Path). For existing code: use
> quarkus-spring-di, quarkus-spring-web, quarkus-spring-data-jpa
> compatibility extensions (Spring annotations work in
> Quarkus). Migration risks: reactive HTTP requires
> @Blocking, JDBC must be on worker threads, ApplicationContext
> events → CDI observers.

**3 minutes (Senior):**

> Migration approaches:
>
> Option 1: Strangler Fig (service-by-service):
>   New services: Quarkus native.
>   Existing services: Spring, migrated incrementally.
>   Add Quarkus gateway in front.
>   Migrate services one at a time.
>   Timeline: 6-18 months for typical microservices.
>
> Option 2: Compatibility extensions:
>   quarkus-spring-di: @Component, @Autowired, @Value.
>   quarkus-spring-web: @RestController, @GetMapping.
>   quarkus-spring-data-jpa: JpaRepository.
>   Low-risk: keep Spring annotations, run on Quarkus.
>   Then migrate annotations over time.
>
> Option 3: Rewrite:
>   Only for small services (<5k LOC).
>   Replace all annotations in one pass.
>   High risk if tests are inadequate.
>
> What changes:
>   @ComponentScan → ArC auto-discovery.
>   @SpringBootApplication → no equivalent (implicit).
>   ApplicationContext → CDI @Inject.
>   @EventListener → @Observes.
>   @Scheduled → quarkus-scheduler @Scheduled.
>   @Cacheable → @CacheResult.
>   spring.application.properties → application.properties
>     (same key names often, but not always).
>
> What stays the same:
>   JPA entities (@Entity, @Column, @ManyToOne).
>   Flyway migrations.
>   REST API contract (same URLs, same JSON).
>   Business logic.
>   Tests (with Mockito/JUnit 5).

**Blank Mind Recovery:**

**(1) Restate:** "You are asking about migrating a Spring
application to Quarkus."

**(2) First principles:** "Migration = change framework,
keep behavior. Minimize risk: incremental, tested."

**(3) Bridge:** "Spring to Quarkus migration is like
changing the engine but keeping the car body."

### 💻 Code Example

```java
// ANNOTATION MAPPING REFERENCE

// Spring                     Quarkus (native CDI)
// @Component                 @ApplicationScoped
// @Service                   @ApplicationScoped
// @Repository                @ApplicationScoped
// @Controller                @Path (JAX-RS)
// @RestController            @Path + @Produces(JSON)
// @Autowired / @Inject       @Inject
// @Value("${prop}")          @ConfigProperty(name="prop")
// @GetMapping("/path")       @GET + @Path("/path")
// @PostMapping               @POST
// @PutMapping                @PUT
// @DeleteMapping             @DELETE
// @RequestBody               method body param
// @PathVariable              @PathParam
// @RequestParam              @QueryParam
// @RequestHeader             @HeaderParam
// @EventListener             void method(@Observes EventType e)
// @Scheduled                 @Scheduled (quarkus-scheduler)
// @Cacheable                 @CacheResult
// @CacheEvict                @CacheInvalidate
// @Transactional             @Transactional (same)
// @Primary                   @Default
// @Qualifier("name")         @Named("name")
// ResponseEntity<T>          Response or Uni<Response>

// EXAMPLE: Spring service -> Quarkus
// Spring:
@Service
public class OrderServiceSpring {

    @Autowired
    private OrderRepository repository;

    @Value("${app.max-orders:100}")
    private int maxOrders;

    @Transactional
    public Order createOrder(
            CreateOrderRequest req) {
        validateLimit(req.getCustomerId());
        return repository.save(
            Order.from(req));
    }

    @EventListener
    public void handleStartup(
            ApplicationReadyEvent event) {
        log.info("OrderService ready");
    }
}

// Quarkus (native CDI):
@ApplicationScoped
public class OrderService {

    @Inject
    OrderRepository repository;

    @ConfigProperty(
        name = "app.max-orders",
        defaultValue = "100")
    int maxOrders;

    @Transactional
    public Order createOrder(
            CreateOrderRequest req) {
        validateLimit(req.getCustomerId());
        return repository.save(Order.from(req));
    }

    void onStart(@Observes StartupEvent ev) {
        log.info("OrderService ready");
    }
}

// EXAMPLE: Spring REST -> Quarkus RESTEasy
// Spring:
@RestController
@RequestMapping("/api/v1/orders")
public class OrderControllerSpring {

    @GetMapping("/{id}")
    public ResponseEntity<OrderDto> findById(
            @PathVariable Long id) {
        return orderService.findById(id)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }
}

// Quarkus:
@Path("/api/v1/orders")
@Produces(MediaType.APPLICATION_JSON)
public class OrderResource {

    @GET
    @Path("/{id}")
    public Uni<Response> findById(
            @PathParam("id") Long id) {
        return orderService.findById(id)
            .map(o -> Response.ok(o).build())
            .onFailure(NotFoundException.class)
            .recoverWithItem(
                Response.status(404).build());
    }
}
```

> **Code walkthrough:** The annotation mapping is nearly
> 1:1 for service classes. The key differences: @Value
> becomes @ConfigProperty, @EventListener becomes @Observes,
> ResponseEntity becomes Response (or Uni<Response> for
> reactive). The controller mapping changes from Spring
> MVC to JAX-RS annotations. The business logic and JPA
> entities remain identical.

**[STAFF] Q1 - How do you de-risk a Spring to
Quarkus migration for a critical service?**

*Why they ask:* Migration risk management.

Step 1: Test coverage first.
Before touching the application: ensure integration
test coverage is >80%. Tests become the safety net.
Tools: JaCoCo for coverage, TestNG/JUnit for existing tests.

Step 2: Start with compatibility extensions.
Add quarkus-spring-di, quarkus-spring-web to the Quarkus app.
Copy Spring code as-is. Run existing tests.
Goal: get the tests passing with zero code changes.

Step 3: Run in shadow mode.
Deploy Quarkus service alongside Spring service.
Route 1% traffic to Quarkus, compare responses.
Dark launch: requests to Spring + Quarkus, compare outputs.
No user-visible change.

Step 4: Migrate annotations incrementally.
Replace @Autowired with @Inject, @Component with @ApplicationScoped.
Run tests after each annotation batch.
Commit often. Roll back is trivial.

Step 5: Remove compatibility extensions.
When no Spring annotations remain: remove quarkus-spring-* deps.
Run full test suite.

Step 6: Enable native image.
Add @RegisterForReflection where needed.
Run @QuarkusIntegrationTest against native binary.

Risk mitigations:
- Feature flags for traffic routing
- Dual deployment during validation
- Monitoring: error rate + latency comparison

*What separates good from great:* Dark launch comparison
before cutting over - ensures zero behavioral differences.

# Quarkus Multi-Module Projects at Scale

**Interview Weight:** high - Multi-module is the
enterprise deployment pattern. Tested for Staff architects.

---

### 🎯 Model Answer

**30 seconds:**

> Large Quarkus projects use Maven/Gradle multi-module
> structure: shared domain modules (entities, DTOs,
> interfaces), service modules (business logic), API
> modules (REST resources), and infrastructure modules
> (repositories, external clients). The application
> module assembles them. Use quarkus-bom for version
> management. Jandex index: add quarkus-jandex to each
> module to ensure classes are discovered by ArC.

**3 minutes (Senior):**

> Multi-module structure:
>
> order-service-parent/
>   order-domain/      (entities, value objects, ports)
>   order-application/ (use cases, services)
>   order-persistence/ (Panache repositories, JPA)
>   order-http/        (JAX-RS resources, DTOs)
>   order-messaging/   (Kafka producers/consumers)
>   order-app/         (assembles, quarkus-maven-plugin)
>
> order-app/pom.xml: only builds + deploys.
>   Other modules: no Quarkus-specific code.
>   Clean architecture: domain has no framework deps.
>
> Jandex index requirement:
>   ArC scans Jandex index.
>   Each module needs its classes indexed.
>   Add to each module (except app):
>     quarkus-jandex or
>     jandex-maven-plugin.
>   Without this: ArC misses beans in sub-modules.
>   Build error: "No bean found for type X."
>
> Dependency management:
>   Import quarkus-bom in parent pom.
>   Child modules: no version on Quarkus deps.
>   Consistent extension versions across modules.
>
> Testing multi-module:
>   Integration tests in order-app module.

// Clean architecture with multi-module

// order-domain/: no framework dependencies
// Pure Java domain model
public class Order {
    private final OrderId id;
    private final CustomerId customerId;
    private OrderStatus status;

    // Domain logic - framework-independent
    public void confirm() {
        if (status != OrderStatus.PENDING) {
            throw new InvalidOrderState(status);
        }
        this.status = OrderStatus.CONFIRMED;
    }
}

// order-domain/: port (interface)
public interface OrderRepository {
    Optional<Order> findById(OrderId id);
    Order save(Order order);
}

// order-persistence/: adapter (Quarkus implementation)
@ApplicationScoped
public class PanacheOrderRepository
        implements OrderRepository {

    @Override
    public Optional<Order> findById(OrderId id) {
        return OrderEntity.findById(id.getValue())
            .map(OrderEntity::toDomain);
    }

    @Override
    @Transactional
    public Order save(Order order) {
        OrderEntity entity =
            OrderEntity.fromDomain(order);
        entity.persist();
        return entity.toDomain();
    }
}

// order-application/: use case
@ApplicationScoped
public class ConfirmOrderUseCase {

    @Inject
    OrderRepository orderRepo;  // Injected by CDI

    @Transactional
    public Order confirm(OrderId orderId) {
        Order order = orderRepo.findById(orderId)
            .orElseThrow(() ->
                new OrderNotFoundException(orderId));
        order.confirm();
        return orderRepo.save(order);
    }
}

**[STAFF] Q1 - Why does ArC miss beans in
sub-modules without the Jandex plugin?**

*Why they ask:* Common multi-module setup bug.

ArC's bean discovery relies on the Jandex index:
a binary file (META-INF/jandex.idx) containing the
annotation metadata of all classes in the module.

Without the index:
1. ArC only scans classes in the application module's
   own classpath (order-app).
2. Classes in order-persistence JARs: not indexed.
3. @ApplicationScoped PanacheOrderRepository: not found.
4. @Inject OrderRepository: unsatisfied dependency.
5. Build error: "No bean found for type OrderRepository."

With jandex-maven-plugin in each module:
1. Plugin generates META-INF/jandex.idx during build.
2. ArC finds the index in each JAR on the classpath.
3. Scans the index for bean annotations.
4. Discovers PanacheOrderRepository.
5. Registers as CDI bean.

Alternative: add quarkus-jandex to each module:
```xml
<!-- order-persistence/pom.xml -->
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-jandex</artifactId>
</dependency>
```

> **Code walkthrough:** This example demonstrates the core pattern in action. The key mechanism shows how the concept works in practice. Study the structure to understand the essential behavior and common usage.

This is simpler than adding the Maven plugin manually.

Diagnostic command:
```bash
# Check if the JAR contains the index
jar tf order-persistence-1.0.jar | grep jandex
# Expected: META-INF/jandex.idx
# If missing: add jandex to the module
```
