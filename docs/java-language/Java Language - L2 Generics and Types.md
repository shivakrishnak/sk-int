# Generics: Type Parameters, Bounds, and Type Safety

**TL;DR** - Generics add compile-time type safety to collections and
algorithms. Bounded type parameters (`<T extends Comparable<T>>`)
constrain what types can be used. Type erasure removes generics at
runtime - the JVM sees raw types.

**Interview Weight:** high - generics appear on every Java interview
and the bounds/wildcards questions separate junior from senior.

---

### 🎯 Model Answer

**30 seconds:**

> Generics let you write type-safe code that works across multiple
> types. `List<String>` guarantees only Strings, caught at compile time.
> Bounded type parameters (`<T extends Comparable<T>>`) constrain what
> types are valid. Type erasure means generic type information is
> removed at runtime - the JVM sees `List`, not `List<String>`.

**3 minutes (Senior):**

> Generics solve the "cast soup" problem of pre-Java 5 code where
> every collection operation required an explicit cast and `ClassCastException`
> would only appear at runtime. With generics, the compiler verifies
> type correctness at the call site.
>
> Bounded type parameters have two forms: upper bound (`extends`)
> restricts to a type and its subtypes; lower bound in wildcards
> (`super`) restricts to a type and its supertypes. For type parameters
> on methods and classes, only upper bounds are supported -
> `<T super Foo>` does not compile.
>
> The critical gotcha is type erasure: at runtime, `List<String>` and
> `List<Integer>` are both just `List`. This means you cannot do
> `new T[]`, `instanceof List<String>`, or use generic type parameters
> in static contexts without explicit `Class<T>` tokens. It is the
> reason for nearly every "unchecked cast" warning you will ever see.

**(2) First principles:** "Without generics, a collection is an object bag.
With generics, the compiler enforces what goes in and what comes out."

**(3) Bridge:** "Generics are like a typed container in a warehouse -

### 📘 Concept Explanation

**The Problem This Solves**

Pre-Java 5:

```java
List list = new ArrayList();
list.add("hello");
String s = (String) list.get(0); // cast required, ClassCastException possible
```

With generics:

```java
List<String> list = new ArrayList<>();
list.add("hello");
String s = list.get(0);  // no cast, type-checked at compile time
```

The cast is still there - it is just generated by the compiler, which
can guarantee it will not fail. This is why generics are called
"compile-time type safety."

**Type Parameters**

- `<T>`: unconstrained - can be any reference type
- `<T extends Bound>`: upper-bounded - T must be Bound or a subtype
- `<T extends A & B>`: multiple bounds - T must be both A and B
  (at most one class, interfaces after)
- Generic methods: `<T> T first(List<T> list)` - T is resolved at
  the call site
- Generic classes: `class Box<T>` - T is resolved when Box is instantiated

**Bounded Type Parameters**

Upper bound on a type parameter:

```java
// T must be Comparable to itself - allows compareTo
<T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}
```

Multiple bounds:

```java
// T must be both Serializable and Cloneable
<T extends Serializable & Cloneable> void store(T item) { ... }
```

**Type Erasure**

At compile time: `List<String>`, `List<Integer>`, `List<T>`.
At runtime: all become `List` (the raw type).

The compiler:

1. Replaces generic types with their bounds (or Object if unbounded)
2. Inserts casts where needed
3. Generates bridge methods for method overriding

Consequences:

- Cannot instantiate generic types: `new T()` does not compile
- Cannot create generic arrays: `new T[10]` does not compile
- Cannot use instanceof with parameterized types:
  `x instanceof List<String>` does not compile
- Static fields and methods cannot use class type parameters

**Mental Model**

> Generics are like a type-labeled container. The label is checked at
> the factory (compile time). At the warehouse (runtime), the label
> is stripped and it is just a container. The factory guarantees you
> only put apples in, so you can be sure apples come out - even though
> the warehouse does not enforce it.

### 💻 Code Example

```java
// BAD: raw types - no type safety
class RawStack {
    private final List stack = new ArrayList();

    public void push(Object item) {
        stack.add(item);
    }

    public Object pop() {
        return stack.remove(stack.size() - 1);
    }
}

// Usage - ClassCastException is a runtime surprise
RawStack s = new RawStack();
s.push("hello");
s.push(42);         // compiles - any Object accepted
String top = (String) s.pop();  // pops 42 - ClassCastException at runtime
```

> **Code walkthrough:** The raw type `List` accepts any Object, so
> `push(42)` compiles. The error appears at runtime when the Integer 42
> is cast to String. This is the pre-generics Java problem - type errors
> are discovered in production, not at the keyboard.

```java
// GOOD: generic class with type parameter
class TypedStack<T> {
    private final List<T> stack = new ArrayList<>();

    public void push(T item) {
        stack.add(item);
    }

    public T pop() {
        if (stack.isEmpty())
            throw new NoSuchElementException("stack is empty");
        return stack.remove(stack.size() - 1);
    }

    public boolean isEmpty() { return stack.isEmpty(); }
}

// Usage - type error caught at compile time
TypedStack<String> s = new TypedStack<>();
s.push("hello");
// s.push(42);  // COMPILE ERROR - 42 is not a String
String top = s.pop();  // no cast needed - type is String
```

> **Code walkthrough:** With `<T>`, the compiler knows `push` takes only
> T and `pop` returns T. When you declare `TypedStack<String>`, T is
> resolved to String throughout. Trying to push an Integer is a compile
> error. No cast is needed on pop. The ClassCastException is impossible.

```java
// Bounded type parameter - constraining what T can be
class SortedList<T extends Comparable<T>> {
    private final List<T> items = new ArrayList<>();

    public void add(T item) {
        items.add(item);
        Collections.sort(items);  // works because T has compareTo
    }

    public T min() {
        if (items.isEmpty())
            throw new NoSuchElementException();
        return items.get(0);
    }

    public T max() {
        if (items.isEmpty())
            throw new NoSuchElementException();
        return items.get(items.size() - 1);
    }
}

// Works with Integer, String, Date - all Comparable<themselves>
SortedList<Integer> ints = new SortedList<>();
ints.add(3); ints.add(1); ints.add(2);
System.out.println(ints.min()); // 1

// SortedList<Object> objects = new SortedList<>(); // COMPILE ERROR
// Object does not implement Comparable<Object>
```

> **Code walkthrough:** `<T extends Comparable<T>>` restricts T to types
> that can compare themselves. This allows `Collections.sort(items)` to
> compile - the compiler can verify that `compareTo` is available on T.
> Attempting to create `SortedList<Object>` fails at compile time because
> Object does not implement `Comparable<Object>`. The bound makes the
> invariant explicit and checked.

**How to test:** Write tests that verify type-incorrect calls fail
compilation (negative test via `@SuppressWarnings`), and that
bounded-type operations work correctly for multiple valid types.

### 🎓 Answers by Seniority

**Junior / Mid:**
"Generics make collections type-safe. `List<String>` only accepts Strings

- the compiler checks this. If you try to add an Integer, it is a
  compile error, not a runtime crash. Bounded type parameters like
  `<T extends Comparable<T>>` restrict what types can be used."

**Senior / Staff:**
"The subtlety with generics that trips up most people is the interaction
between type erasure and runtime behavior. Because types are erased,
you lose the ability to check or create instances of generic types at
runtime. The workaround is passing `Class<T>` tokens explicitly.

A practical example: if you need to create instances of T inside a
generic class, you must do:

```java
class Factory<T> {
    private final Class<T> type;
    Factory(Class<T> type) { this.type = type; }
    T create() throws ReflectiveOperationException {
        return type.getDeclaredConstructor().newInstance();
    }
}
```

This is verbose but necessary because the JVM has erased T.

Another common pitfall: heap pollution. When you mix raw types with
generic types - say, assigning a `List` to a `List<String>` via an
unchecked cast - the guarantee breaks. You get the heap containing
Integer where String is expected, and the ClassCastException appears
at a seemingly unrelated location later, making it hard to trace."

### 🚨 Failure Modes and Diagnosis

**FM1 - Heap Pollution from unchecked cast**

_Symptom:_ `ClassCastException` at a location far from where the
bad cast actually occurred. Stack trace points to a line that
just reads from a list.

_Root Cause:_ Mixing raw types with generic types via unchecked cast.

_Diagnostic:_

```java
// The culprit (somewhere upstream)
List list = new ArrayList();  // raw type
list.add(42);
List<String> strings = (List<String>) list;  // unchecked warning

// The symptom (somewhere downstream - appears innocent)
String s = strings.get(0);  // ClassCastException: Integer cannot be cast to String
```

Find the heap pollution source by enabling `-Xlint:unchecked` and
treating all unchecked warnings as errors.

_Fix:_ Eliminate raw types. If receiving a raw type from legacy code,
validate elements before casting:

```java
if (list.stream().allMatch(String.class::isInstance)) {
    List<String> safe = (List<String>) list;  // safe after check
}
```

_Prevention:_ Add `-Xlint:unchecked -Werror` to javac flags in CI.

**FM2 - Generic type not available at runtime (erasure)**

_Symptom:_ `GenericSignatureFormatError`, unexpected behavior when
trying to inspect generic types at runtime.

_Root Cause:_ Type erasure removes generic information. Code that
tries to use `T.class` or instantiate `new T()` fails.

_Fix:_ Pass explicit `Class<T>` tokens:

```java
// WRONG
class Deserializer<T> {
    T deserialize(byte[] data) {
        return objectMapper.readValue(data, T.class);  // T.class doesn't exist
    }
}

// RIGHT - pass the class token
class Deserializer<T> {
    private final Class<T> type;
    Deserializer(Class<T> type) { this.type = type; }

    T deserialize(byte[] data) throws Exception {
        return objectMapper.readValue(data, type);
    }
}
```

**[JUNIOR] Q1 - Conceptual**
_What problem do generics solve?_

Pre-generics, every collection was a "bag of Objects." Every insertion
accepted anything; every retrieval required a cast that could fail at
runtime. `ClassCastException` appeared in production, not at compile
time.

Generics move the type check to compile time. The compiler rejects
type-incorrect inserts. No runtime casts are needed for retrieval.

The cost: the type information exists only at compile time (type
erasure). The benefit: zero runtime overhead, because the erased
code is identical to what you would have written manually with casts.

_What separates good from great:_ Mentioning that type erasure means
the solution is a compile-time trick - there is no runtime enforcement
except for the casts the compiler inserts.

---

**[JUNIOR] Q2 - Hands-on**
_What is the difference between `<T>` and `<T extends Comparable<T>>`?_

`<T>`: T is unconstrained - can be any reference type. Inside the
method/class, the compiler only knows T is an Object. You can store
and retrieve T values, but you cannot call any T-specific methods.

`<T extends Comparable<T>>`: T must implement `Comparable<T>`. Inside
the method/class, the compiler knows T has a `compareTo(T)` method.
You can compare T values, sort collections of T, find min/max.

```java
// Works with any T
<T> T identity(T x) { return x; }

// Only works when T is Comparable to itself
<T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}

max(3, 5);        // works - Integer implements Comparable<Integer>
max("a", "b");    // works - String implements Comparable<String>
// max(new Object(), new Object()); // COMPILE ERROR - Object not Comparable
```

_What separates good from great:_ Explaining that the bound enables
the compiler to allow method calls on T - without a bound, only Object
methods are available.

---

**[SENIOR] Q3 - Trade-off**
_Why are Java generics invariant, and how do wildcards address this?_

Invariance means `List<Integer>` is NOT a subtype of `List<Number>`,
even though `Integer` is a subtype of `Number`. This seems wrong
intuitively - why not?

The reason: if `List<Integer>` were a subtype of `List<Number>`, this
would compile:

```java
List<Integer> ints = new ArrayList<>();
List<Number> nums = ints;  // if this were allowed...
nums.add(3.14);            // add a Double to what is really a List<Integer>
Integer i = ints.get(0);  // ClassCastException - 3.14 is not Integer
```

Invariance prevents this hole. Wildcards provide flexibility when
you only need read or write access, not both:

- `List<? extends Number>`: can read as Number; cannot add (type unknown)
- `List<? super Integer>`: can add Integer; read returns Object

_What separates good from great:_ The above unsafe example - showing
WHY invariance is necessary, not just that it exists.

---

**[SENIOR] Q4 - Production**
_How does type erasure affect runtime behavior? Give a real example._

Jackson's `ObjectMapper.readValue()` is the canonical example. To
deserialize into a generic type, you cannot pass `List<User>.class`
(does not compile). Instead, Jackson uses `TypeReference`:

```java
// BAD - erased to List.class at runtime
List<User> users = mapper.readValue(json, List.class);
// Each element is actually LinkedHashMap, not User

// GOOD - TypeReference captures generic type via superclass token
List<User> users = mapper.readValue(json,
    new TypeReference<List<User>>() {}
);
```

`TypeReference<List<User>>{}` works because while `List<User>.class`
does not exist, a subclass of `TypeReference<List<User>>` can be
reflected to retrieve its generic supertype - `List<User>` survives
because it is a supertype parameter, not a local type variable.

_What separates good from great:_ Explaining WHY TypeReference works -
the supertype token trick.

---

**[STAFF] Q5 - Architecture**
_What are the design trade-offs of type erasure vs reified generics
(as in C# or Kotlin)?_

Java chose erasure for backward compatibility. Pre-generics code
(`List l = new ArrayList()`) needed to interoperate with generic
code. If generics were reified (available at runtime), you could not
assign a `List<String>` to a raw `List` variable safely.

Reified generics (C#):

- `List<int>` and `List<string>` are distinct runtime types
- Enables `typeof(T)`, `new T()`, `x is List<string>`
- No heap pollution - runtime type information is always correct
- Cost: code bloat (each parameterization is a new type), no
  interoperability with raw/legacy code

Erasure (Java):

- `List<String>` and `List<Integer>` are the same runtime type
- Enables full backward compatibility with pre-generic code
- Heap pollution is possible via unchecked casts
- Cannot use T in reflection or create instances of T
- Zero code size penalty - one compiled copy serves all types

For the Java ecosystem (huge legacy codebase, strong back-compat
contract), erasure was the only viable choice. Kotlin addresses this
with `reified` inline functions - the compiler inlines the function
at each call site, making T available as a real type locally.

_What separates good from great:_ Explaining the Java social contract
(backward compatibility above all) as the reason for erasure.

### ⚖️ Comparison Table

| Aspect        | Raw Types                | Generics               | Wildcards                                        |
| ------------- | ------------------------ | ---------------------- | ------------------------------------------------ |
| Type safety   | None - runtime casts     | Full compile-time      | Partial - read or write only                     |
| Runtime       | Object (same as generic) | Object after erasure   | Object after erasure                             |
| instanceof    | Works                    | Works (raw only)       | Works (raw only)                                 |
| Legacy compat | Full                     | Good (backward compat) | Good                                             |
| Use case      | Legacy code only         | New code always        | API flexibility                                  |
| Variance      | N/A                      | Invariant              | Covariant (? extends) or contravariant (? super) |

**Deciding factor:** Always use generics in new code. Raw types are
for interacting with legacy code only. Wildcards are for method
signatures that need to accept a range of generic types.

# Wildcards and PECS: Producer Extends, Consumer Super

**TL;DR** - Wildcards enable flexible generic method signatures.
PECS is the mnemonic for choosing: if a generic structure produces
values you will read, use `extends`. If it consumes values you will
write, use `super`.

**Interview Weight:** high - wildcard questions appear in every
mid-to-senior Java interview and most candidates get PECS backwards.

---

### 🎯 Model Answer

**30 seconds:**

> Wildcards let generic methods accept a range of parameterized types.
> PECS: Producer Extends, Consumer Super. If you are reading from a
> collection (it produces values), use `? extends T`. If you are
> writing to a collection (it consumes values), use `? super T`. If
> you need both, use a concrete type parameter.

**3 minutes (Senior):**

> The wildcard restrictions exist because of type safety. `List<? extends Number>`
> means "a list of some specific Number subtype, but we don't know which."
> Because we don't know the exact subtype, we cannot add anything -
> we might add a Double to a List<Integer>. But we can safely read
> elements as Number.
>
> `List<? super Integer>` means "a list of Integer or some supertype."
> Because Integer is a subtype of everything in the list, we can safely
> add Integer values. But reading returns Object - we have no guarantee
> about the exact element type.
>
> The practical application: `Collections.copy` uses both:
> `copy(List<? super T> dest, List<? extends T> src)`. The source
> list produces T values (extends), the destination consumes them
> (super). This is why the method works with any compatible types,
> not just the exact same parameterization.

**Blank Mind Recovery:**

**(1) Restate:** "You are asking about PECS and wildcards -
let me cover when to use extends versus super and why
neither allows both."

**(2) First principles:** "A wildcard is an unknown type within
a bound. Extends means unknown subtype - reading as T is
safe, writing is not. Super means unknown supertype -
writing T is safe, reading yields only Object."

**(3) Bridge:** "PECS names the collection's role: a vending
machine produces snacks (? extends - you read from it).
A bin consumes cans (? super - you write into it). Choose
the bound that names what the collection does."

---

### 📘 Concept Explanation

**Unbounded Wildcard `<?>`**

Means "a list of some unknown type." You can read elements as Object.
You cannot add anything (except null). Use when the code is truly
type-agnostic:

```java
void printSize(List<?> list) {
    System.out.println(list.size());  // does not need to know element type
}
```

**Upper Bounded Wildcard `<? extends T>`**

Means "a list of T or a subtype of T." Covariant.

- CAN read elements as T
- CANNOT add elements (type of subtype is unknown)

```java
double sumNumbers(List<? extends Number> list) {
    double sum = 0;
    for (Number n : list) sum += n.doubleValue();  // read as Number - OK
    // list.add(1.5);  // COMPILE ERROR - might be List<Integer>
    return sum;
}
// Works with List<Integer>, List<Double>, List<BigDecimal>
```

**Lower Bounded Wildcard `<? super T>`**

Means "a list of T or a supertype of T." Contravariant.

- CAN add T values (T is a subtype of the actual element type)
- READ returns Object (actual element type unknown - might be supertype)

```java
void addNumbers(List<? super Integer> list) {
    list.add(1);    // OK - Integer is always valid for ? super Integer
    list.add(42);   // OK
    Object o = list.get(0);  // returns Object - that's all we know
    // Integer i = list.get(0);  // COMPILE ERROR
}
// Works with List<Integer>, List<Number>, List<Object>
```

**PECS Applied**

The `Collections.copy` signature demonstrates PECS perfectly:

```java
public static <T> void copy(
    List<? super T> dest,    // Consumer: we write T into it (super)
    List<? extends T> src    // Producer: we read T from it (extends)
) { ... }
```

**When to use which:**

| Need                          | Wildcard               | Reason                       |
| ----------------------------- | ---------------------- | ---------------------------- |
| Read values as T              | `<? extends T>`        | Any subtype is readable as T |
| Write T values                | `<? super T>`          | Any supertype accepts T      |
| Both read and write           | `<T>` (type parameter) | Need the exact type          |
| Don't care about element type | `<?>`                  | Truly type-agnostic          |

**Mental Model**

> extends/super wildcards are like a machine's input/output ports.
> A "Numbers output" port (`? extends Number`) can be plugged into
> any slot that accepts Numbers - you get Numbers out but cannot put
> anything in (you don't know the exact model). A "Numbers input"
> port (`? super Number`) accepts any Number - you can put Numbers in
> but when something falls out the other end, you only know it is
> an Object.

### 💻 Code Example

```java
// BAD: overly restrictive - method only works with exact same type
// Cannot accept List<Integer> where List<Number> is expected
static double sum(List<Number> list) {
    double total = 0;
    for (Number n : list) total += n.doubleValue();
    return total;
}

List<Integer> ints = List.of(1, 2, 3);
// sum(ints);  // COMPILE ERROR - List<Integer> is not List<Number>
```

> **Code walkthrough:** Generic invariance means `List<Integer>` is not
> a subtype of `List<Number>`. The method with `List<Number>` parameter
> only accepts exactly `List<Number>`. This is unnecessarily restrictive
> since the method only reads from the list.

```java
// GOOD: upper bound wildcard - accepts any Number subtype list
static double sum(List<? extends Number> list) {
    double total = 0;
    for (Number n : list) total += n.doubleValue();  // read as Number - OK
    return total;
    // Cannot add to list - type of subtype is unknown
}

List<Integer> ints = List.of(1, 2, 3);
List<Double> doubles = List.of(1.1, 2.2, 3.3);
sum(ints);    // works
sum(doubles); // works
```

> **Code walkthrough:** `<? extends Number>` tells the compiler this is
> a read-only operation from the perspective of the list's element type.
> Any `List<Subtype of Number>` is acceptable. The compiler prevents
> adding elements because adding an Integer to what might be a
> `List<Double>` would break type safety.

```java
// PECS in practice: fill a collection with values
static void fill(
    List<? super Integer> dest,  // Consumer: accepts Integer or supertype
    int count,
    int value
) {
    for (int i = 0; i < count; i++) {
        dest.add(value);  // add Integer to ? super Integer - always safe
    }
}

List<Integer> intList = new ArrayList<>();
List<Number> numList = new ArrayList<>();
List<Object> objList = new ArrayList<>();

fill(intList, 5, 42);  // works - Integer super Integer
fill(numList, 5, 42);  // works - Number super Integer
fill(objList, 5, 42);  // works - Object super Integer
// fill(List<Double>, 5, 42);  // COMPILE ERROR - Double not super Integer
```

> **Code walkthrough:** `? super Integer` means the list can hold
> Integer or any supertype of Integer. Adding an `int` (auto-boxed
> to Integer) is always valid because Integer is always a valid element
> for any `? super Integer` list. The method is maximally flexible -
> it works with any list that can hold Integers.

**How to test:** Verify that sum() accepts List<Integer>, List<Double>,
List<BigDecimal>. Verify that fill() accepts List<Integer>, List<Number>,
List<Object> but not List<Double>.

### 🎓 Answers by Seniority

**Junior / Mid:**
"PECS: Producer Extends, Consumer Super. If a collection gives you
values (you read), use extends. If you put values in (you write),
use super. `<? extends Number>` is for reading; `<? super Integer>`
is for writing."

**Senior / Staff:**
"The PECS rule has a deeper structure: covariance and contravariance.
`? extends T` is covariant - subtype lists are usable where supertype
lists are needed (for reading). `? super T` is contravariant - supertype
lists are usable where subtype lists are needed (for writing).

The reason for the restriction is the same in both cases: type safety.
With `? extends T`, the actual type is unknown - we can guarantee
reads are T but cannot guarantee inserts are safe. With `? super T`,
the actual type is unknown upward - we can guarantee Integer inserts
are safe but cannot guarantee what type reads will be.

In practice, the most common use is making API methods more flexible.
The `Comparator<? super T>` parameter in TreeMap and sort methods
is contravariance in practice: any Comparator for a supertype of T
can compare T values - a `Comparator<Object>` can compare anything.
This lets you define one comparator for a base type and reuse it
everywhere."

**FM1 - API too restrictive due to missing wildcard**

_Symptom:_ Users of your library must cast or create adapter objects

_Root Cause:_ Method parameter uses exact type instead of bounded
wildcard.

_Diagnostic:_

// Test: can the method accept subtypes?

**FM2 - `? extends` wildcard blocks needed mutation**

_Symptom:_ Method needs to both read and write to a collection but
`? extends` is blocking adds.

_Root Cause:_ Using a wildcard when a type parameter is needed.

_Fix:_ Use a concrete type parameter instead of a wildcard:

```java
// WRONG for read+write
void addAndSum(List<? extends Number> list) {
    list.add(1.5);  // COMPILE ERROR - cannot add to ? extends
}

// RIGHT - concrete type parameter
<T extends Number> void addAndSum(List<T> list, T value) {
    list.add(value);   // can add - type is known as T
    for (T n : list) { /* process */ }
}
```

**[MID] Q1 - Conceptual**
_What is the PECS rule and why does it exist?_

PECS: **P**roducer **E**xtends, **C**onsumer **S**uper.

When a generic container is a **producer** (you read values from it),
use `? extends T`. When it is a **consumer** (you write values to it),
use `? super T`.

Why: the restrictions are type safety requirements. `? extends T` does
not allow adds because the actual subtype is unknown - adding to a
`List<? extends Number>` might add a Double to a List<Integer>. You
can safely read as Number because any subtype IS-A Number.

`? super T` does not give you back T on reads because the actual
supertype is unknown - you might get a Number or an Object. You can
safely add T because T IS-A everything in `? super T`.

_What separates good from great:_ The WHY - not just the rule but
the type safety reason behind each restriction.

---

**[SENIOR] Q2 - Production**
_Where in the Java standard library does PECS appear? Walk through
the reasoning._

`Collections.sort(List<T> list, Comparator<? super T> c)`:

The comparator is a consumer of T values. It takes two T values and
returns an ordering. By using `? super T`, the API accepts:

- `Comparator<T>` (exact match)
- `Comparator<Supertype of T>` (if a parent comparator exists)

Practical value: define one `Comparator<Shape>` based on area.
Use it to sort `List<Circle>` without having a `Comparator<Circle>`.
This is contravariance - a more general comparator can be used in
a more specific context.

`Collections.copy(List<? super T> dest, List<? extends T> src)`:
src produces T values (reading from it -> extends).
dest consumes T values (writing to it -> super).
This allows copying from `List<Integer>` into `List<Number>` - the
source is a producer of Integer, the destination is a consumer of
Number (and Number super Integer).

_What separates good from great:_ The copy example where `src` and
`dest` have different wildcard bounds - showing how PECS enables
flexible cross-type operations.

**[STAFF] Q3 - Architecture**
_How would you design a generic pipeline API using PECS principles?_

A data processing pipeline where stages can be connected:

```java
interface Stage<I, O> {
    O process(I input);
}

class Pipeline<T> {
    private final List<T> data;

    // Source produces T (extends allows subtypes)
    static <T> Pipeline<T> from(List<? extends T> source) {
        return new Pipeline<>(new ArrayList<>(source));
    }

    // Map: produces R from T
    <R> Pipeline<R> map(Function<? super T, ? extends R> fn) {
        // ? super T: accepts function that takes T or supertype
        // ? extends R: accepts function that returns R or subtype
        List<R> result = new ArrayList<>();
        for (T item : data) result.add(fn.apply(item));
        return new Pipeline<>(result);
    }

    // Collect: consumer takes T (super)
    void collect(List<? super T> destination) {
        destination.addAll(data);
    }
}

// Usage
List<Integer> source = List.of(1, 2, 3);
List<Number> dest = new ArrayList<>();

Pipeline.from(source)                  // ? extends Integer
    .map(Integer::doubleValue)         // ? super Integer, ? extends Double
    .collect(dest);                    // ? super Double - dest is Number
```

The Function type `Function<? super T, ? extends R>` is the canonical
PECS application for transformation: accepts T (or supertype) as input,
produces R (or subtype) as output. This matches Java's `Stream.map`.

_What separates good from great:_ The Function parameter design -
showing that PECS applies to function types too, not just collections.

### ⚖️ Comparison Table

| Wildcard             | Read           | Write            | Use when                       |
| -------------------- | -------------- | ---------------- | ------------------------------ |
| `<T>` type parameter | Yes, as T      | Yes, T values    | Need both read and write       |
| `<? extends T>`      | Yes, as T      | No (except null) | Read-only: producing T values  |
| `<? super T>`        | Only as Object | Yes, T values    | Write-only: consuming T values |
| `<?>` unbounded      | Only as Object | No (except null) | Type-agnostic operations       |

**Deciding factor:** Apply PECS at API design time to maximize
flexibility. Use the most restrictive wildcard that satisfies the
method's actual operations. Wildcards in return types are usually
wrong - return a concrete type so callers can use the value.

# Enums: State Machines, Abstract Methods, and EnumMap

**TL;DR** - Java enums are full classes, not just integer constants.
They can have fields, methods, and even per-constant abstract methods.
EnumMap and EnumSet are the fastest collection implementations because
they use array-backed ordinal indexing.

**Interview Weight:** medium - the per-constant method body pattern
is frequently tested at mid-to-senior level.

---

### 🎯 Model Answer

**30 seconds:**

> Java enums are type-safe named constants implemented as classes.
> Each constant is a singleton instance. Enums can have fields,
> constructors, and methods. Per-constant method bodies let each
> constant override behavior - this is a compile-safe state machine.
> EnumMap uses ordinal-indexed arrays - faster than HashMap for
> enum keys.

**3 minutes (Senior):**

> The power of Java enums beyond simple constants is the ability
> to embed behavior. A common pattern is the strategy-per-constant:
> define an abstract method in the enum, and each constant provides
> its own implementation. This replaces a switch statement that
> would otherwise need updating every time a constant is added or
> removed. The compiler enforces exhaustiveness - if a constant
> does not implement the abstract method, compilation fails.
>
> EnumMap and EnumSet exploit the fact that enum constants have
> ordinals (0, 1, 2...) and the total count is fixed. EnumMap uses
> a plain array indexed by ordinal - O(1) operations with no hashing.
> EnumSet uses a single long bitmask for up to 64 constants. Both
> are faster and more memory-efficient than their HashMap/HashSet
> counterparts for enum keys.

**Blank Mind Recovery:**

**(1) Restate:** "You are asking about Java enums - let me

**(2) First principles:** "An enum is a fixed set of
named singletons. Each constant is an object that can hold

**(3) Bridge:** "An enum with abstract methods is like a

### 📘 Concept Explanation

**Enums Are Classes**

```java
// This is syntactic sugar for a class with singleton constants
enum Planet {
    MERCURY(3.303e+23, 2.4397e6),
    VENUS(4.869e+24, 6.0518e6),
    EARTH(5.976e+24, 6.37814e6);

    private final double mass;     // each constant has a field
    private final double radius;

    Planet(double mass, double radius) {  // enum constructor
        this.mass = mass;
        this.radius = radius;
    }

    double surfaceGravity() {
        final double G = 6.67300E-11;
        return G * mass / (radius * radius);
    }
}
```

**Per-Constant Method Bodies (Abstract Method Pattern)**

```java
enum Operation {
    PLUS  { @Override public int apply(int x, int y) { return x + y; } },
    MINUS { @Override public int apply(int x, int y) { return x - y; } },
    TIMES { @Override public int apply(int x, int y) { return x * y; } },
    DIVIDE{
        @Override
        public int apply(int x, int y) {
            if (y == 0) throw new ArithmeticException("div by zero");
            return x / y;
        }
    };

    public abstract int apply(int x, int y);
}
```

Each constant implements the abstract method. Adding a new constant
without the method is a compile error.

**EnumMap and EnumSet**

```java
// EnumMap: array-based, no hashing, O(1) ops
EnumMap<DayOfWeek, String> schedule = new EnumMap<>(DayOfWeek.class);
schedule.put(DayOfWeek.MONDAY, "standup 9am");
schedule.put(DayOfWeek.FRIDAY, "retrospective 3pm");

// EnumSet: bitmask-based, compact, super-fast
EnumSet<DayOfWeek> workdays = EnumSet.range(
    DayOfWeek.MONDAY, DayOfWeek.FRIDAY
);
EnumSet<DayOfWeek> weekend = EnumSet.complementOf(workdays);
```

**Built-in Enum Methods**

- `name()`: constant name as String
- `ordinal()`: position (0-based) - avoid in persistence
- `values()`: array of all constants
- `valueOf(String)`: constant by name (throws if not found)
- `EnumSet.allOf(Class)`, `EnumSet.noneOf(Class)`: full/empty sets

**When to Use Enum for State Machines**

Enums are ideal when:

- The state space is closed and known at compile time
- Transitions have associated logic
- You need compile-time exhaustiveness for switch expressions

### 💻 Code Example

```java
// BAD: integer constants - no type safety, no behavior
class OrderStatus {
    public static final int PENDING = 0;
    public static final int PROCESSING = 1;
    public static final int SHIPPED = 2;
    public static final int DELIVERED = 3;
}

void updateStatus(int status) {
    if (status == OrderStatus.PENDING) { /* ... */ }
    // Nothing prevents: updateStatus(999) - invalid at runtime
}
```

> **Code walkthrough:** Integer constants provide no type safety.
> `updateStatus(999)` compiles fine. Adding a new status requires
> finding all switch/if statements that process status - there is no
> compile-time enforcement that all cases are handled.

```java
// GOOD: enum with per-constant behavior - compile-safe state machine
enum OrderStatus {
    PENDING {
        @Override
        public OrderStatus nextStatus() { return PROCESSING; }
        @Override
        public boolean canCancel() { return true; }
    },
    PROCESSING {
        @Override
        public OrderStatus nextStatus() { return SHIPPED; }
        @Override
        public boolean canCancel() { return false; }
    },
    SHIPPED {
        @Override
        public OrderStatus nextStatus() { return DELIVERED; }
        @Override
        public boolean canCancel() { return false; }
    },
    DELIVERED {
        @Override
        public OrderStatus nextStatus() {
            throw new IllegalStateException(
                "DELIVERED is a terminal state"
            );
        }
        @Override
        public boolean canCancel() { return false; }
    };

    public abstract OrderStatus nextStatus();
    public abstract boolean canCancel();
}

// Usage - type-safe, behavior-correct
void processOrder(Order order) {
    if (!order.getStatus().canCancel()) {
        throw new IllegalStateException("Cannot cancel this order");
    }
    order.setStatus(OrderStatus.PENDING.nextStatus());
}
```

> **Code walkthrough:** The abstract method `nextStatus()` and
> `canCancel()` are implemented per-constant. Adding a new status
> without implementing both methods is a compile error - no constants
> can escape the contract. The state transition logic lives with the
> state definition. `switch` statements on status are unnecessary -
> `status.nextStatus()` dispatches correctly.

**How to test:** Test each constant's behavior directly; test state
transitions; test that terminal states throw correctly.

**[SENIOR] Q2 - Trade-off**
_When would you use an enum state machine vs a proper state

- States are few (less than ~10)
- Transitions are deterministic and synchronous
- Business rules for state transitions are stable
- The codebase is small and the state machine is localized

- States are many with complex transitions
- Transitions have guards, actions, and entry/exit behaviors
- Audit trail of transitions is required

file becomes unmaintainable. At that point, extracting to a proper
state machine pattern is warranted.

# Autoboxing, Unboxing, and the Integer Cache Trap

**TL;DR** - Autoboxing automatically converts primitives to wrapper
objects. The Integer cache (-128 to 127) makes `==` work for small
integers, breaking equality comparison for larger values. In
performance-sensitive code, autoboxing in tight loops creates
significant GC pressure.

**Interview Weight:** medium - the cache trap is a classic interview
trick question that reveals depth.

---

### 🎯 Model Answer

**30 seconds:**

> Autoboxing converts `int` to `Integer` automatically. Unboxing does
> the reverse. The Integer cache pools instances from -128 to 127 -
> so `Integer.valueOf(127) == Integer.valueOf(127)` is true but
> `Integer.valueOf(128) == Integer.valueOf(128)` is false. Always
> use `.equals()` for Integer comparison, never `==`.

**3 minutes (Senior):**

> Autoboxing was introduced in Java 5 to reduce the friction of using
> primitives with collections (which only hold objects). The compiler
> translates `Integer i = 42` into `Integer i = Integer.valueOf(42)`.
> The reverse, `int i = integer`, becomes `integer.intValue()`.
>
> The Integer cache is a JVM optimization that pools Integer objects
> for values -128 to 127. `Integer.valueOf()` returns a cached instance
> for values in this range. This means `==` comparison works correctly
> for small integers (you get the same object back). For values outside
> the range, new objects are created and `==` compares references -
> returning false even for equal values.
>
> The performance impact: every autoboxing operation allocates an object
> on the heap (for out-of-cache values). In a tight loop that boxes
> millions of integers, this creates significant GC pressure. JMH
> profiling commonly shows autoboxing-heavy code spending 30-40% of
> CPU on allocation and GC.

**Blank Mind Recovery:**

**(1) Restate:** "You are asking about autoboxing and the
Integer cache - let me walk through the compiler translation
and the equality trap."

**(2) First principles:** "The compiler inserts
Integer.valueOf() wherever an object is needed. The JVM
caches instances from -128 to 127. Outside that range new
objects are created, so == compares references not values."

**(3) Bridge:** "The Integer cache is like a coin tray:
small coins are reused from the tray. A large-value bill
always comes from the vault as a new note. Never compare
bills with ==. Always use .equals()."

### 📘 Concept Explanation

**What Autoboxing Does**

The compiler translates these automatically:

```
int -> Integer:    Integer i = 42; → Integer i = Integer.valueOf(42);
Integer -> int:    int i = integer; → int i = integer.intValue();
```

Applies for method arguments, collection operations, arithmetic,
and assignment whenever the context requires the opposite type.

**The Integer Cache**

`Integer.valueOf(int)` caches instances for values -128 to 127.
The upper bound is configurable via JVM flag
`-XX:AutoBoxCacheMax=<value>` (but the lower bound is always -128).

Why 127? Historical: this range covers the most common small-integer
use cases. The cache exists in `Integer.IntegerCache` as a static
array initialized at class load.

```java
Integer a = 127;    // Integer.valueOf(127) - cached instance
Integer b = 127;    // same cached instance
a == b;             // true - same object reference

Integer c = 128;    // Integer.valueOf(128) - new object
Integer d = 128;    // another new object
c == d;             // false - different objects
c.equals(d);        // true - same value
```

**All Wrapper Caches**

| Wrapper       | Cache range                      |
| ------------- | -------------------------------- |
| Integer       | -128 to 127 (configurable upper) |
| Long          | -128 to 127                      |
| Short         | -128 to 127                      |
| Byte          | -128 to 127 (entire range)       |
| Character     | '\u0000' to '\u007F' (0-127)     |
| Boolean       | TRUE and FALSE (always cached)   |
| Float, Double | No cache                         |

**NullPointerException from Unboxing**

```java
Map<String, Integer> counts = new HashMap<>();
int n = counts.get("missing");  // NPE - unboxing null to int
```

This is one of the most surprising NPEs - the code looks like it
accesses an int, but the unboxing call `intValue()` on null throws.

**Performance Impact**

```java
// This allocates a new Long object on every iteration
long sum = 0L;      // primitive - fine
Long result = 0L;   // boxed - starts with Long(0)
for (long i = 0; i < 1_000_000; i++) {
    result += i;    // unbox result, add i, rebox -> new Long each time
}
// ~1 million Long allocations in the loop
```

---

### 💻 Code Example

```java
// BAD: == comparison for Integer - fails outside cache range
Integer a = 1000;
Integer b = 1000;

if (a == b) {              // FALSE - reference comparison
    System.out.println("equal");
} else {
    System.out.println("not equal");  // always prints this for 1000
}
```

> **Code walkthrough:** This is the Integer cache trap. `1000` is
> outside the -128 to 127 cache range, so `Integer.valueOf(1000)`
> creates a new object each time. `a == b` compares object references,
> not values. The output is "not equal" even though both hold the
> value 1000. This bug is invisible in tests that use small values.

```java
// GOOD: always use .equals() for wrapper comparison
Integer a = 1000;
Integer b = 1000;

if (a.equals(b)) {           // TRUE - value comparison
    System.out.println("equal");
}

// Or: unbox to primitives when comparing numerically
if (a.intValue() == b.intValue()) {  // also correct
    System.out.println("equal");
}

// Modern: Objects.equals for null safety
if (Objects.equals(a, b)) {  // null-safe value comparison
    System.out.println("equal");
}
```

> **Code walkthrough:** The three correct alternatives all compare
> values rather than references. `.equals()` is the idiomatic choice.
> `intValue() ==` is explicit about the unboxing. `Objects.equals`
> handles the case where either Integer might be null without throwing.

```java
// Performance: primitives vs boxed in hot path
// BAD: boxing in tight loop
long sumBoxed(List<Integer> values) {
    Long sum = 0L;  // boxed accumulator - boxes on every +=
    for (Integer v : values) {
        sum += v;   // unbox v, add, rebox sum -> allocation per iter
    }
    return sum;
}

// GOOD: primitive accumulator
long sumPrimitive(List<Integer> values) {
    long sum = 0L;  // primitive - no boxing
    for (Integer v : values) {
        sum += v;   // unbox v to int, widen to long, add to primitive
    }              // only unboxing - no re-boxing of sum
    return sum;
}
```

> **Code walkthrough:** The difference is the accumulator type.
> `Long sum` boxes the result of every addition - ~1 million Long
> allocations for a million-element list. `long sum` is a primitive -
> only the input Integer is unboxed per iteration, no re-boxing.
> JMH profiling shows the primitive version 5-10x faster for large
> lists due to eliminated allocation and GC pressure.

**How to test:** Write a test that specifically compares Integer
instances with value 128+ using both `==` and `.equals()` to document
the expected behavior.

   Works correctly in unit tests (usually small values in the
   cache range), fails in production with larger values.

For performance: Vavr, Eclipse Collections, and Trove provide
int-keyed maps (IntObjectHashMap) that avoid boxing entirely for
primitive keys. For numeric processing, streaming with
`mapToInt`/`mapToLong` keeps values as primitives throughout the
pipeline."

### ⚠️ Common Misconceptions

| #   | Misconception                                   | Reality                                                                                                                     | Danger                                                              |
| --- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 1   | "Integer == Integer always works"               | Only for -128 to 127 (cached range). Outside this range, == compares references.                                            | Correct tests (small values) masking production bug (large values)  |
| 2   | "Autoboxing is free (no cost)"                  | Every autobox allocates a heap object for out-of-cache values. In tight loops, this is measurable GC pressure.              | Performance degradation in hot paths                                |
| 3   | "NPE cannot come from int access"               | `int n = map.get(key)` unboxes the Integer return. If the key is missing, get() returns null, and unboxing null throws NPE. | Confusing NPEs that look like they occur at int operations          |
| 4   | "The cache range is exactly -128 to 127 always" | The upper bound is configurable via -XX:AutoBoxCacheMax. In some JVMs with custom settings, the range is larger.            | Relying on cache behavior in tests that will fail on different JVMs |
| 5   | "Long, Short, Byte have no caching"             | All integer wrapper types cache -128 to 127. Boolean caches TRUE and FALSE. Only Float and Double have no cache.            | Assuming Double and Long behave differently from Integer            |

### 🚨 Failure Modes and Diagnosis

**FM1 - NullPointerException from unboxing map result**

_Symptom:_ NPE at a line that reads: `int count = counts.get(key)`.
The stack trace seems wrong - it is not a null dereference.

_Root Cause:_ `Map.get()` returns null if the key is absent.
Unboxing null Integer to int throws NPE.

_Diagnostic:_

```bash
# Find potential unboxing NPE sites
grep -rn "int .* = .*\.get\|long .* = .*\.get" src/ --include="*.java"
# Each result needs null check before unboxing
```

_Fix:_

```java
// BAD
int count = counts.get("key");  // NPE if key absent

// GOOD options:
int count = counts.getOrDefault("key", 0);  // Java 8+
int count = counts.containsKey("key") ? counts.get("key") : 0;
Integer raw = counts.get("key");
int count = raw != null ? raw : 0;
```

_Prevention:_ Never unbox a Map.get() result without null check
or getOrDefault().

**FM2 - Boxed accumulator GC pressure under load**

_Symptom:_ High GC throughput, short GC pauses under load, profiler
shows many short-lived Integer/Long objects in young gen.

_Root Cause:_ Boxed accumulator in aggregate computation loop.

_Diagnostic:_

```bash
# JVM flags to observe allocation pressure
java -XX:+PrintGCDetails -XX:+PrintGCDateStamps -jar app.jar
# High "Allocation Rate" in young gen = autoboxing candidate

# Async-profiler for allocation profiling
asprof -e alloc -d 30 -f flamegraph.html <pid>
# Look for Integer.valueOf or Long.valueOf in hot path
```

_Fix:_ Change boxed accumulator to primitive type.

**[JUNIOR] Q1 - Conceptual**
_What is the Integer cache, and why can it cause bugs?_

Java caches Integer objects for values -128 to 127. When you call
`Integer.valueOf(50)`, you always get back the same object. When
you call `Integer.valueOf(200)`, you get a new object each time.

The bug: `==` compares object references in Java (for non-primitives).
For cached values, two Integers with the same value are the same
object - `==` returns true. For non-cached values, they are different
objects - `==` returns false even though the values are equal.

Fix: always use `.equals()` for Integer comparison. Never use `==`
for wrapper types.

```java
Integer x = 100; Integer y = 100;
x == y;      // true  (cached)
x.equals(y); // true

Integer a = 200; Integer b = 200;
a == b;      // false (not cached - different objects)
a.equals(b); // true
```

_What separates good from great:_ Noting that this bug hides in tests
because test data often uses small values that happen to be in the
cache range.

---

**[MID] Q2 - Debugging**
_You have code that compares Integer values with == and it works
in tests but fails in production. What is happening?_

The Integer cache trap. The code uses `==` to compare Integer
objects. In tests, the Integer values happen to fall in the -128
to 127 cache range, so `==` compares the same cached instances
and returns true.

In production, real data contains values outside the cache range.
For those, `==` compares different object references and returns
false - even though the values are logically equal.

Diagnosis:

1. Find all `==` comparisons involving Integer/Long/Short variables
2. Verify the test values are small (within cache range)
3. Verify production values can be outside that range

Fix: replace all `integer1 == integer2` with `integer1.equals(integer2)`
or unbox to primitives first: `int1 == int2` where int1/int2 are
the `.intValue()` of each.

_What separates good from great:_ Explaining why tests pass - they
typically use IDs or counts that start at 1 and are small enough
to be cached.

---

**[SENIOR] Q3 - Production**
_How do you profile and fix autoboxing-related GC pressure?_

Three-step process:

1. **Identify the hot path**: use JFR (Java Flight Recorder) or
   async-profiler in allocation mode. Look for methods that allocate
   significant numbers of Integer/Long/Double objects.

```bash
asprof -e alloc -d 60 -f alloc-flamegraph.html <pid>
# Open flamegraph - look for Integer.valueOf in hot areas
```

2. **Measure the impact**: run JMH benchmarks comparing boxed and
   primitive versions:

```java
@Benchmark
public long boxedSum(BenchmarkState state) {
    Long sum = 0L;
    for (Integer i : state.data) sum += i;
    return sum;
}

@Benchmark
public long primitiveSum(BenchmarkState state) {
    long sum = 0L;
    for (Integer i : state.data) sum += i;
    return sum;
}
```

3. **Fix**: change boxed accumulators to primitives. For primitive-
   keyed maps, use `IntObjectHashMap` from Eclipse Collections or
   use `HashMap<Integer, V>` with `getOrDefault` to avoid boxing
   during lookups.

_What separates good from great:_ Starting with profiling before
optimizing - knowing where autoboxing actually costs vs where it
is irrelevant.

| Type                       | Memory                         | GC pressure        | Null handling       | Collection eligible |
| -------------------------- | ------------------------------ | ------------------ | ------------------- | ------------------- |
| `int`                      | 4 bytes                        | None               | No (cannot be null) | No                  |
| `Integer`                  | 16 bytes (object header + int) | Yes (out of cache) | Yes                 | Yes                 |
| Cached Integer (-128..127) | 0 (reuse)                      | None               | Yes                 | Yes                 |
| `long`                     | 8 bytes                        | None               | No                  | No                  |
| `Long`                     | 24 bytes                       | Yes (out of cache) | Yes                 | Yes                 |

**Deciding factor:** Use primitives everywhere performance matters.
Use boxed types when nullability is needed, or when collections
require object types. Use `getOrDefault` to avoid unboxing NPE on
map lookups.

# Type Inference: Diamond Operator, var, and Target Typing

**TL;DR** - Java has three type inference mechanisms: the diamond
operator (`<>`) for generic instantiation, `var` for local variable
type inference (Java 10+), and target typing for lambda parameters.
All reduce boilerplate while preserving static typing.

**Interview Weight:** medium - var usage and its limits are
increasingly common in Java interviews.

---

### 🎯 Model Answer

**30 seconds:**

> Java infers types in three contexts: the diamond operator lets you
> skip repeating generic type arguments in constructors, var infers
> the type of local variables from the right-hand side, and target
> typing lets lambdas omit parameter types. All are compile-time
> inference - the static type is still fixed, just written once.

**3 minutes (Senior):**

> The diamond operator (`<>`) was Java 7's first inference step:
> `new ArrayList<>()` infers `ArrayList<String>` from the declaration
> type. It saved repeating the same type parameter twice.
>
> `var` (Java 10) goes further: `var list = new ArrayList<String>()`
>
> - the variable type is inferred from the initializer. The variable
>   still has a static type; it is not dynamic like Python. The IDE knows
>   the type; the JVM knows the type; only the source code omits it.
>
> The `var` limits are explicit by design: no uninitialized var,
> no null initializer, no use in fields, method parameters, or return
> types. These limits ensure the inferred type is always unambiguous.
> The intent: use var when the type is obvious from context (especially
> for long generic types); use explicit types when they add clarity.

**Blank Mind Recovery:**

**(1) Restate:** "You are asking about Java type inference -
let me cover diamond, var, and target typing for lambdas."

**(2) First principles:** "Type inference is the compiler
deducing the static type so you don't write it twice. The
type is fixed and checked at compile time - only the source
omits it. var requires an initializer so the type is clear."

**(3) Bridge:** "var is like a self-labeling box: you fill
it once, the box labels itself, and the label never changes.
You wrote the contents once, not the contents plus a
matching label."

---

### 📘 Concept Explanation

**Diamond Operator**

Before Java 7:

```java
Map<String, List<Integer>> map = new HashMap<String, List<Integer>>();
```

With diamond (Java 7+):

```java
Map<String, List<Integer>> map = new HashMap<>();
// Compiler infers HashMap<String, List<Integer>> from the LHS type
```

Cannot be used with anonymous classes (pre-Java 9). Java 9 allows
it for anonymous classes when the inferred type is denotable.

**`var` for Local Variables**

Rules:

- Must be initialized in the same statement
- Initializer cannot be null
- Cannot be used in fields, method parameters, return types
- Cannot be used for uninitialized variables
- Cannot be used in catch blocks (use the actual exception type)

```java
var list = new ArrayList<String>();     // ArrayList<String>
var map = new HashMap<String, Long>();  // HashMap<String, Long>
var entry = map.entrySet().iterator()   // Iterator<Map.Entry<String,Long>>
               .next();
```

**Target Typing for Lambdas**

```java
// Compiler infers parameter types from the functional interface context
Comparator<String> c = (a, b) -> a.compareTo(b);
// a and b inferred as String from Comparator<String>

// Without target typing inference
Comparator<String> c = (String a, String b) -> a.compareTo(b);
// Explicit - same result, more verbose
```

**When `var` Improves vs Hurts Readability**

Improves:

- Long generic types: `var entries = map.entrySet()` vs
  `Set<Map.Entry<String, List<Integer>>> entries = map.entrySet()`
- Local loop variables: `for (var entry : map.entrySet())`
- Chained builder calls where the type is obvious

Hurts:

- Method return calls where the type is not obvious:
  `var result = process(input)` - what is result?
- Primitive containers where precision matters:
  `var x = 3.14` - is this double? float? (it is double, but
  easy to misread)
- Code review of unfamiliar code where the type adds documentation
  value

---

### 💻 Code Example

```java
// BAD: verbose repetition of type parameters
List<Map.Entry<String, List<Integer>>> entries =
    new ArrayList<Map.Entry<String, List<Integer>>>();

Map<String, Map<String, List<Integer>>> nested =
    new HashMap<String, Map<String, List<Integer>>>();
```

> **Code walkthrough:** The type is specified four times across two
> declarations. Every repetition is a chance to introduce a typo.
> The cognitive load of reading these declarations adds noise without
> adding information.

```java
// GOOD: diamond + var eliminate repetition
List<Map.Entry<String, List<Integer>>> entries = new ArrayList<>();
// Diamond infers: ArrayList<Map.Entry<String, List<Integer>>>

var nested = new HashMap<String, Map<String, List<Integer>>>();
// var infers: HashMap<String, Map<String, List<Integer>>>
// Type still exists; just written once on the RHS
```

> **Code walkthrough:** Diamond keeps the declaration type explicit
> (important for the API contract visible to callers in the same scope)
> while avoiding the constructor-side repetition. `var` keeps the
> constructor type explicit (the actual concrete type) while making
> the declaration short. Neither changes the static type - the compiler
> sees the full type in both cases.

```java
// var with streams - clarity vs verbosity tradeoff
// Verbose but explicit
Stream<Map.Entry<String, Long>> stream =
    counts.entrySet().stream()
          .filter(e -> e.getValue() > 100L);

// var - shorter, type obvious from context
var stream = counts.entrySet().stream()
                   .filter(e -> e.getValue() > 100L);

// BAD var usage - type not obvious
var result = compute(config);  // what is result? Cannot tell without
                               // reading compute's signature
```

> **Code walkthrough:** The key question for var is: "Is the inferred
> type obvious to a reader who cannot hover over the variable?" For
> stream operations, the element type is visible in context. For
> opaque method return values, explicit types are better documentation.

**How to test:** var does not require different testing - tests exercise
behavior, not declaration syntax. Test that the inferred type supports
the operations you call on it.

### 🚨 Failure Modes and Diagnosis

**FM1 - var with raw type**

_Symptom:_ Unchecked warning: "uses unchecked or unsafe operations."

_Root Cause:_ `var list = new ArrayList()` infers raw `ArrayList`,
not a parameterized type.

_Fix:_ Always include the type parameter with var:

```java
var list = new ArrayList<String>();   // correct - ArrayList<String>
var list = new ArrayList();           // raw type - avoid
```

**FM2 - Diamond on method call with ambiguous return**

_Symptom:_ Compile error: "cannot infer type arguments."

_Root Cause:_ Diamond (`<>`) can only be used in `new` expressions.
It cannot infer types for method return values or cast expressions.

_Fix:_ Use `var` for method return assignments, or provide explicit
type parameters.

**[JUNIOR] Q1 - Conceptual**
_What does `var` actually do in Java?_

`var` tells the compiler to infer the variable's type from the
initializer expression. The compiler determines the exact type at
compile time; the variable still has a fixed static type.

```java
var i = 42;              // int
var d = 3.14;            // double
var s = "hello";         // String
var list = new ArrayList<String>();  // ArrayList<String>
```

`var` is not dynamic typing. After inference, the variable is as
strongly typed as if you had written the type explicitly:

```java
var x = 42;
x = "hello";  // COMPILE ERROR - x was inferred as int
```

Limits: local variables only, must be initialized, cannot be null.

_What separates good from great:_ Immediately clarifying that var
is static - not dynamic like JavaScript let/var.

---

**[MID] Q2 - Trade-off**
_When should you use var vs explicit types? What is the guideline?_

Use var when the type is obvious from the right-hand side or does
not add informational value:

- Constructor calls: `var map = new HashMap<String, Integer>()`
- Iterator variables: `for (var entry : map.entrySet())`
- Long parameterized types where repetition is noise

Use explicit types when the type is the documentation:

- Method return values with opaque names: `List<User> users = getUsers()`
  is more readable than `var users = getUsers()`
- Any case where a reviewer would need to look up the return type
  to understand what the variable holds
- Public or package-private declarations (though var is only for
  locals anyway)

The test: ask "if I remove the IDE hover, would a reader know the
type?" If yes, var is fine. If no, use the explicit type.

_What separates good from great:_ The specific "IDE hover test" -
a concrete guideline rather than a vague "use your judgment."

---

**[SENIOR] Q3 - Production**
_How has var affected code review and maintainability in practice?_

In my experience, var reduces noise in method bodies where the type
is already visible on the right-hand side. The most impactful use
is in enhanced for loops over complex collections:

```java
// Before var
for (Map.Entry<String, List<Order>> entry : ordersByCustomer.entrySet()) {
    String customerId = entry.getKey();
    List<Order> orders = entry.getValue();
    processOrders(customerId, orders);
}

// With var
for (var entry : ordersByCustomer.entrySet()) {
    var customerId = entry.getKey();
    var orders = entry.getValue();
    processOrders(customerId, orders);
}
```

The second version is easier to scan. The type is visible in the
`ordersByCustomer` declaration; repeating it in the loop adds noise.

The maintainability risk: if the map type changes, the var-based
loop adapts silently. This is generally good (less to change) but
occasionally masks that the loop logic needs updating.

Code review guideline I apply: var is fine for local temporaries
within a method. Anything that crosses a method boundary (parameter,
return type) must be explicit.

_What separates good from great:_ A specific example with before/after
showing where var helps vs the note about silent adaptation.

| ---------------------- | -------------------------- | ----------------------- | ---------------------------- |

| Inferred from          | Declaration type (LHS)     | Initializer (RHS)       | Functional interface context |
| Available since        | Java 7                     | Java 10                 | Java 8                       |
| Scope                  | new expressions only       | Local variables only    | Lambda expressions           |
